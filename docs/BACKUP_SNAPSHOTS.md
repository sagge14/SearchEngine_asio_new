# Формат резервных снимков

`BackupEngine` создаёт полные независимые снимки. Каждый опубликованный каталог
можно восстановить без базовой копии и без применения других версий.

## Структура

```text
<backup_dir>/
  <имя-источника>_<хеш-полного-пути>/
    cache/
      files/
        <хеш-относительного-пути>/
          gen_<номер>/
            artifact
            metadata.txt
    snapshots/
      YYYYMMDD_HHMMSS/
        manifest.txt
        data/
          ...полная копия источника...
```

Если за одну секунду требуется несколько снимков, к имени добавляется
шестизначный суффикс:

```text
YYYYMMDD_HHMMSS_000001
```

Хеш полного нормализованного пути изолирует источники с одинаковыми именами.
Ротация работает только внутри каталога конкретного источника.

`cache/` — внутренний проверенный пофайловый кэш. Он ускоряет подготовку
снимка и позволяет не повторять уже успешную работу после ошибки другого
файла. Снимки не содержат ссылок или жёстких ссылок на кэш: каждый файл
физически копируется в `snapshots/.../data/`. Кэш можно удалить — уже
опубликованные снимки продолжат работать.

Пример для `D:\BASES_PRD`:

```text
F:\AutoPadBackups\
  BASES_PRD_973ede13a28f60af\
    cache\
      files\
        4d388c2712edbdf4\
          gen_137930492011422144_8\
            artifact
            metadata.txt
    snapshots\
      20260730_120000\
        manifest.txt
        data\
          ARCHIVE.db3
          PARAMETERS.db3
          EXPORT.ini
          METH_BASES\
            02-2026.db3
      20260730_121500\
        manifest.txt
        data\
          ARCHIVE.db3
          PARAMETERS.db3
          EXPORT.ini
          METH_BASES\
            02-2026.db3
```

Имена хешей и поколений кэша служебные и на восстановление не влияют.

## Создание снимка

В режиме `auto`:

1. Копия создаётся в каталоге `.partial_*`.
2. Если задано `skip_unchanged: true`, источник сравнивается с сохранёнными
   состояниями файлов в последнем манифесте. При полном совпадении и успешной
   проверке последнего снимка новая версия не создаётся.
3. Если `cache: true`, для каждого файла проверяется его последняя
   подтверждённая копия в пофайловом кэше.
4. Для SQLite в режимах журналирования `DELETE`, `TRUNCATE` и `PERSIST`
   сигнатура читается внутри read-транзакции. В неё входят режим журнала,
   размер, время изменения и заголовок SQLite с change counter.
5. Если сигнатура не изменилась, кэшированный файл повторно проверяется по
   размеру, хешу и `PRAGMA integrity_check`, после чего физически копируется
   в новый полный снимок.
6. Изменившиеся SQLite-файлы (`.db`, `.db3`, `.sqlite`, `.sqlite3` или файл
   с заголовком `SQLite format 3`) копируются через SQLite Online Backup API.
7. Небольшая база копируется за один шаг под краткой shared-блокировкой.
   Читатели продолжают работу, а фиксация конкурентной записи ждёт окончания
   копирования.
8. Для полученной базы выполняется `PRAGMA integrity_check`. При включённом
   кэше готовый файл атомарно публикуется в пофайловом кэше; при выключенном
   кэше Online Backup сразу создаёт файл снимка.
9. SQLite в режиме `WAL` намеренно не переиспользуется из постоянного кэша и
   не считается неизменившейся: для неё каждый раз выполняется Online Backup.
10. Обычные файлы копируются и кэшируются только после повторной проверки
   размера, времени изменения и содержимого.
11. SQLite sidecar-файлы `-journal`, `-wal` и `-shm` не включаются.
12. Если состав исходного каталога изменился во время прохода, снимок
   отклоняется и будет повторён следующим запуском.
13. После успешной подготовки всех файлов записывается `manifest.txt`.
14. Каталог атомарно переименовывается в окончательное имя.
15. После публикации удаляются версии сверх `max_versions`.

Режим `filesystem` сохраняет прежнее поведение: источник сравнивается с
последним снимком и копируется как набор обычных файлов. Для рабочих SQLite
этот режим применять нельзя.

Ошибка копирования или проверки не публикует снимок и не затрагивает уже
существующие версии. При этом успешно обновлённые записи пофайлового кэша
сохраняются. Следующая попытка повторяет только изменившиеся или ранее
неудачные файлы.

## Восстановление

Для восстановления `D:\BASES_PRD`:

1. Остановить все локальные программы и отключить сетевых пользователей,
   работающих с базами.
2. Выбрать каталог снимка и убедиться, что в нём есть `manifest.txt`.
3. Переименовать текущий `D:\BASES_PRD`, например в
   `D:\BASES_PRD_before_restore_20260730`. Это одновременно убирает старые
   `-journal`, `-wal` и `-shm`.
4. Создать новый `D:\BASES_PRD`.
5. Скопировать **всё содержимое** выбранного `data\` в новый
   `D:\BASES_PRD`, сохранив подкаталоги.
6. Запустить одну программу, проверить открытие баз и нужные данные, затем
   вернуть сетевой доступ.

При разделённом расписании сначала восстанавливается последний полный снимок
каталога. Если отдельный снимок `ARCHIVE.db3` имеет более позднее время, его
файл из `data\ARCHIVE.db3` копируется поверх `ARCHIVE.db3` полного снимка.
Все программы и сетевые пользователи в этот момент должны оставаться
остановленными.

Например, для снимка выше копируется содержимое:

```text
F:\AutoPadBackups\BASES_PRD_973ede13a28f60af\
  snapshots\20260730_121500\data\
```

в:

```text
D:\BASES_PRD\
```

Для отдельного файла нужный файл находится в `data/<исходное-имя-файла>`.
Перед заменой отдельной рабочей SQLite также требуется остановить всех
пользователей и убрать старый файл вместе с его sidecar-файлами.

`manifest.txt` содержит:

```text
format=4
created=YYYYMMDD_HHMMSS
type=file|directory
mode=auto|filesystem
source=<исходный путь>
sqlite_version=<версия SQLite BackupService>
cache=verified-per-file|disabled
skip_unchanged=true|false
files=<количество записей>
entry=<метод><TAB><размер><TAB><относительный путь>
source_state=<сигнатура источника><TAB><относительный путь>
```

Метод `sqlite-online` означает свежий Online Backup, `sqlite-cache` —
проверенную неизменившуюся SQLite из кэша, `stable-file` — свежую копию
обычного файла, `file-cache` — его проверенную кэшированную копию.

## Совместимость

Каталоги старой реализации (`*_backup`, `*_base` и старые каталоги изменений)
не используются новым движком, не участвуют в ротации и автоматически не
удаляются.

Символические ссылки по-прежнему пропускаются. ACL, альтернативные потоки NTFS
и другие специальные метаданные в формат снимка не входят.
