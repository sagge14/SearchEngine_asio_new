Конспект: Работа инвертированного индекса

Цель документа: Подробное объяснение архитектуры и работы инвертированного индекса в поисковой системе.

1. Общая архитектура

1.1. Что такое инвертированный индекс?

Инвертированный индекс — это структура данных, которая позволяет быстро находить документы по словам. В отличие от прямого индекса (документ → слова), инвертированный индекс хранит: слово → список документов, где это слово встречается.

Пример:
Документ 1: "кот собака"
Документ 2: "кот мышь"
Документ 3: "собака мышь"

Инвертированный индекс:
"кот" → [документ 1, документ 2]
"собака" → [документ 1, документ 3]
"мышь" → [документ 2, документ 3]

2. Структуры данных

2.1. Posting — запись о вхождении слова в документ

Проблема

Нужно хранить информацию о том, в каких документах встречается слово и сколько раз.

Решение

Структура Posting содержит минимальную информацию:

struct Posting {
    uint32_t fileId;  // ID документа (4 байта)
    uint16_t cnt;     // Количество вхождений слова в документ (2 байта)
};

Разбор синтаксиса

  • uint32_t fileId — идентификатор файла (32-битное беззнаковое число). Максимум 4 миллиарда файлов.
  • uint16_t cnt — счетчик вхождений (16-битное беззнаковое число). Максимум 65535 вхождений одного слова в документ.
Оптимизация памяти: Всего 6 байт на постинг. Для миллиона постингов это всего ~6 МБ.

2.2. PostingList — упорядоченный список постингов

Проблема

Для каждого слова нужно хранить список документов, где оно встречается. Нужен быстрый поиск и вставка.

Решение

Класс PostingList использует отсортированный std::vector<Posting>:

class PostingList {
    std::vector<Posting> data;  // Отсортированный по fileId
    
public:
    // Поиск по fileId (бинарный поиск)
    const uint16_t* find(uint32_t fileId) const {
        auto it = std::lower_bound(data.begin(), data.end(), fileId,
                                   [](const Posting& p, uint32_t id) { 
                                       return p.fileId < id; 
                                   });
        return (it != data.end() && it->fileId == fileId) ? &(it->cnt) : nullptr;
    }
    
    // Добавление/обновление (вставка в отсортированную позицию)
    uint16_t& operator[](uint32_t fileId) {
        auto it = std::lower_bound(data.begin(), data.end(), fileId, ...);
        if (it != data.end() && it->fileId == fileId) {
            return it->cnt;  // Найдено — возвращаем ссылку
        }
        // Не найдено — вставляем новый элемент
        it = data.insert(it, { fileId, 0 });
        return it->cnt;
    }
};

Как это работает?

  1. Хранение: Постинги хранятся в отсортированном порядке по fileId.
  2. Поиск: Используется бинарный поиск (std::lower_bound) — O(log n).
  3. Вставка: Находится позиция бинарным поиском, затем вставка — O(n) в худшем случае.
  4. Обновление: Если постинг существует, просто увеличиваем счетчик.
Важно: Вставка в середину вектора требует сдвига элементов. Для частых вставок это может быть медленно, но для индексации это приемлемо, так как постинги добавляются пакетами.

2.3. WordIdManager — двусторонний словарь слов

Проблема

Слова — это строки, которые занимают много памяти. Нужно преобразовывать слова в компактные числовые ID для эффективного хранения.

Решение

Класс WordIdManager реализует двустороннее преобразование:

class WordIdManager {
    std::unordered_map<std::string, uint32_t> word2id_;  // слово → ID
    std::vector<std::string>                  id2word_;  // ID → слово
    
public:
    // Получить ID слова (создать новый, если нужно)
    uint32_t getId(const std::string& word) {
        auto [it, inserted] = word2id_.try_emplace(word, id2word_.size());
        if (inserted) {
            id2word_.push_back(word);  // Добавляем в обратный словарь
        }
        return it->second;
    }
    
    // Обратное преобразование: ID → слово
    const std::string& byId(uint32_t id) const {
        return id2word_[id];
    }
};

Как это работает?

  1. Прямое преобразование: При первом обращении к слову создается новый ID (равный текущему размеру вектора).
  2. Обратное преобразование: ID используется как индекс в векторе id2word_ — O(1) доступ.
  3. Память: Каждое слово хранится один раз в id2word_, а не дублируется в каждом постинге.
Преимущество: Вместо хранения строк "кот", "собака" в каждом постинге, хранится только число (4 байта). Экономия памяти огромная!

2.4. Chunk — блок постинг-листов для параллелизма

Проблема

При параллельной индексации нескольких файлов одновременно, разные потоки могут пытаться обновлять постинги для разных слов. Нужна блокировка, но блокировать весь словарь целиком — слишком медленно.

Решение

Словарь разбивается на чанки (блоки) по 4096 постинг-листов. Каждый чанк имеет свой мьютекс:

struct Chunk {
    std::vector<PostingList> bucket;  // 4096 постинг-листов
    std::shared_mutex mutex;          // Мьютекс для этого чанка
    
    Chunk() : bucket(CHUNK_SIZE) {}  // CHUNK_SIZE = 4096
};

Как это работает?

  1. Разбиение: WordId делится на CHUNK_SIZE (4096) для получения индекса чанка: 
    size_t chunkIndex = wordId / CHUNK_SIZE;  // В каком чанке
size_t localIndex = wordId % CHUNK_SIZE;   // Позиция в чанке
  2. Параллелизм: Потоки, работающие с разными чанками, не блокируют друг друга.
  3. Блокировки: Только потоки, работающие с одним чанком, синхронизируются через shared_mutex.
Пример: Если у нас 10000 уникальных слов, то будет 3 чанка (0-4095, 4096-8191, 8192-10000). Потоки, индексирующие слова из разных чанков, работают параллельно без блокировок!

3. Процесс индексации файла

3.1. Общий поток индексации

Последовательность операций:
1. Сканирование файлов → получение списка путей
2. Определение изменений (diff) → новые/обновленные/удаленные
3. Удаление старых записей
4. Параллельная индексация файлов
5. Сохранение индекса на диск

3.2. fileIndexing() — индексация одного файла

Проблема

Нужно извлечь все слова из файла, посчитать частоты и добавить в индекс.

Решение

Метод fileIndexing() выполняет следующие шаги:

void InvertedIndex::fileIndexing(FileId fileId, 
                                  std::shared_ptr<std::promise<void>> promise)
{
    // 1. Открываем файл
    std::wstring fullPath = docPaths.pathById(fileId);
    std::ifstream file(fullPath.c_str(), std::ios::binary);
    
    // 2. Словарь частот слов в файле
    robin_hood::unordered_map<std::string, size_t> freqWordFile;
    
    // 3. SIMD токенизация (чтение по 64 КБ)
    static const size_t BUF_SIZE = 64 * 1024;
    std::vector<char> buf(BUF_SIZE);
    std::string carry;  // Хвост слова на границах буферов
    
    while (true) {
        file.read(buf.data(), BUF_SIZE);
        std::size_t readBytes = file.gcount();
        if (readBytes == 0) break;
        
        // SIMD токенизация с OEM-866 кодировкой
        simd_tokenizer::tokenize_oem866_buffer(
            buf.data(), readBytes, file.eof(), carry,
            [&](std::string_view tok) {
                std::string w;
                w.assign(tok.data(), tok.size());
                OEMFastTokenizer::normalizeToken(w);  // Нормализация
                if (!w.empty())
                    ++freqWordFile[w];  // Подсчет частоты
            });
    }
    
    // 4. Создаем batch и отправляем на обработку
    PostingBatch batch;
    batch.fileId = fileId;
    batch.list.reserve(freqWordFile.size());
    for (auto &[word, count] : freqWordFile)
        batch.list.emplace_back(word, count);
    
    applyBatchInStrand(std::move(batch));
}

Разбор по шагам

  1. Открытие файла: Получаем путь по FileId и открываем файл в бинарном режиме.
  2. Токенизация: Используется SIMD-оптимизированный токенизатор для быстрого разбора текста на слова. Чтение происходит блоками по 64 КБ.
  3. Нормализация: Каждое слово нормализуется (приведение к верхнему регистру для OEM-866).
  4. Подсчет частот: Используется быстрая хеш-таблица robin_hood::unordered_map для подсчета частот слов.
  5. Создание batch: Создается пакет данных для дальнейшей обработки в strand (последовательном потоке).
SIMD токенизация: Использует векторные инструкции процессора для параллельной обработки нескольких символов одновременно. Это значительно ускоряет разбор текста.

3.3. processBatch() — обработка пакета слов

Проблема

Нужно преобразовать слова в WordId, сгруппировать по чанкам и обновить постинги.

Решение

void InvertedIndex::processBatch(const PostingBatch& batch)
{
    // 1. Преобразуем слова → WordId и суммируем частоты
    robin_hood::unordered_map<uint32_t, uint32_t> widMap;
    for (auto& [word, count] : batch.list) {
        uint32_t wid = wordIds.getId(word);  // Получаем/создаем ID
        widMap[wid] += count;  // Суммируем частоты
        
        // Обновляем wordRefs (какие слова есть в файле)
        auto& refv = wordRefs[batch.fileId];
        if (refv.empty() || refv.back() != wid)
            refv.push_back(wid);
    }
    
    // 2. Группировка по chunkId для минимизации блокировок
    std::unordered_map<size_t, std::vector<PostingTask>> chunkMap;
    for (auto& [wid, count] : widMap) {
        size_t chunkIndex = wid / CHUNK_SIZE;
        chunkMap[chunkIndex].push_back({ batch.fileId, wid, count });
    }
    
    // 3. Отправляем на commit в CPU pool
    boost::asio::post(cpu_pool_, [this, chunkMap = std::move(chunkMap)]() {
        commitChunkMap(chunkMap);
    });
}

Как это работает?

  1. Преобразование слов: Каждое слово преобразуется в WordId через wordIds.getId(). Если слово новое, создается новый ID.
  2. Суммирование: Если одно слово встречается несколько раз в batch (редко, но возможно), частоты суммируются.
  3. Группировка по чанкам: Постинги группируются по чанкам, чтобы минимизировать количество блокировок.
  4. Асинхронный commit: Обновление постингов выполняется в CPU pool асинхронно.
Оптимизация: Группировка по чанкам позволяет обновить все постинги одного чанка за одну блокировку, вместо блокировки для каждого слова отдельно.

3.4. commitChunkMap() — атомарное обновление чанков

Проблема

Нужно безопасно обновить постинги в разных чанках, минимизируя время блокировок.

Решение

void InvertedIndex::commitChunkMap(
    const std::unordered_map<size_t, std::vector<PostingTask>>& chunkMap)
{
    // 1. Расширяем массив чанков ОДИН раз (под глобальным мьютексом)
    {
        std::lock_guard<std::mutex> g(mapMutex);
        size_t maxIndex = 0;
        for (auto& [cid, _] : chunkMap)
            if (cid > maxIndex) maxIndex = cid;
        
        if (maxIndex >= dictionaryChunks.size())
            dictionaryChunks.resize(maxIndex + 1);
        
        // Создаем недостающие чанки
        for (auto& [cid, _] : chunkMap)
            if (!dictionaryChunks[cid])
                dictionaryChunks[cid] = std::make_unique<Chunk>();
    }
    
    // 2. Обновляем каждый чанк с минимальной блокировкой
    for (auto& [cid, tasks] : chunkMap) {
        Chunk& ch = *dictionaryChunks[cid];
        std::unique_lock<std::shared_mutex> lk(ch.mutex);  // Блокируем только этот чанк
        
        for (auto& t : tasks) {
            size_t local = t.wordId % CHUNK_SIZE;
            ch.bucket[local][t.fileId] += t.count;  // Обновляем постинг
        }
    }
}

Как это работает?

  1. Подготовка: Под глобальным мьютексом расширяем массив чанков и создаем недостающие. Это делается один раз для всего batch.
  2. Обновление: Для каждого чанка берем его локальный мьютекс и обновляем все постинги этого чанка. Потоки, работающие с другими чанками, не блокируются.
  3. Атомарность: Операция ch.bucket[local][t.fileId] += t.count выполняется под блокировкой, гарантируя корректность при параллельных обновлениях.
Важно: Глобальный мьютекс mapMutex используется только для расширения массива чанков (редкая операция). Основная работа идет с локальными мьютексами чанков, что обеспечивает высокий параллелизм.

4. Параллелизм и синхронизация

4.1. Архитектура потоков

Три уровня параллелизма:

1. CPU Pool (cpu_pool_)
- Параллельная индексация файлов
- Токенизация и извлечение слов
- Количество потоков = количество ядер CPU

2. Strand (strand_)
- Последовательная обработка batch'ей
- Преобразование слов → WordId
- Группировка по чанкам
- Гарантирует порядок операций

3. IO Context (io_commit_)
- Асинхронный commit постингов
- Обновление чанков
- Минимальные блокировки

4.2. Strand — последовательная обработка

Проблема

При параллельной индексации нескольких файлов, разные потоки могут одновременно вызывать wordIds.getId() для одного и того же нового слова. Это может привести к созданию дубликатов ID или гонкам данных.

Решение

Используется boost::asio::strand — гарантирует, что все операции выполняются последовательно в одном потоке:

void InvertedIndex::applyBatchInStrand(PostingBatch batch)
{
    // Все операции в strand выполняются последовательно
    boost::asio::post(strand_, [this, batch = std::move(batch)]() mutable {
        processBatch(batch);  // Преобразование слов → WordId
    });
}

Как это работает?

  1. Стратегия: Все batch'и из разных файлов попадают в одну очередь strand.
  2. Последовательность: Strand обрабатывает их один за другим, гарантируя атомарность операций с wordIds.
  3. Параллелизм: Файлы индексируются параллельно (токенизация), но обновление словаря происходит последовательно.
Компромисс: Strand создает узкое место, но это необходимо для корректности данных. На практике это не критично, так как токенизация (CPU-intensive) выполняется параллельно, а обновление словаря (быстрая операция) — последовательно.

4.3. Chunk-based блокировки

Проблема

Если бы весь словарь был защищен одним мьютексом, параллелизм был бы нулевым — только один поток мог бы обновлять индекс одновременно.

Решение

Словарь разбит на чанки, каждый со своим мьютексом:

struct Chunk {
    std::vector<PostingList> bucket;  // 4096 постинг-листов
    std::shared_mutex mutex;          // Локальный мьютекс чанка
};

Преимущества

  • Параллелизм: Потоки, работающие с разными чанками, не блокируют друг друга.
  • Масштабируемость: Чем больше чанков, тем выше параллелизм.
  • Гранулярность: Блокируется только нужный чанк, а не весь словарь.
Пример: При индексации 8 файлов параллельно на 8-ядерном процессоре, если слова распределены по разным чанкам, все 8 потоков могут обновлять постинги одновременно без блокировок друг друга!

5. Удаление файлов из индекса

5.1. safeEraseFileInternal() — безопасное удаление

Проблема

При удалении файла нужно удалить все постинги этого файла из всех слов. Но если файлов много, полный обход всех слов будет очень медленным.

Решение

Используется структура wordRefs — обратный индекс (файл → список слов):

void InvertedIndex::safeEraseFileInternal(FileId fileId)
{
    // Используем wordRefs для быстрого поиска слов файла
    auto itRefs = wordRefs.find(fileId);
    if (itRefs != wordRefs.end()) {
        const auto& widList = itRefs->second;  // Список WordId этого файла
        
        // Удаляем постинг только для этих слов
        for (uint32_t wid : widList) {
            size_t chunkIndex = wid / CHUNK_SIZE;
            size_t localIndex = wid % CHUNK_SIZE;
            
            if (chunkIndex >= dictionaryChunks.size()) continue;
            
            auto& chunkPtr = dictionaryChunks[chunkIndex];
            if (!chunkPtr) continue;
            
            Chunk& chunk = *chunkPtr;
            std::unique_lock<std::shared_mutex> lk(chunk.mutex);
            auto& posting = chunk.bucket[localIndex];
            if (!posting.empty())
                posting.erase(fileId);  // Удаляем постинг
        }
        
        wordRefs.erase(itRefs);  // Удаляем запись из wordRefs
    }
    else {
        // Fallback: полный обход (редкий случай)
        // ... обход всех чанков и всех постингов
    }
}

Как это работает?

  1. Быстрый путь: Используется wordRefs[fileId] для получения списка WordId, которые есть в этом файле.
  2. Точечное удаление: Удаляются постинги только для этих слов, а не для всех слов в словаре.
  3. Fallback: Если wordRefs отсутствует (старый индекс), выполняется полный обход.
Оптимизация: Вместо обхода всех слов в словаре (может быть миллионы), обходим только слова конкретного файла (обычно сотни-тысячи). Ускорение в сотни раз!

5.2. wordRefs — обратный индекс

Проблема

Нужно быстро найти все слова, которые есть в конкретном файле, для эффективного удаления.

Решение

Структура wordRefs хранит обратное отображение:

std::unordered_map<size_t, std::vector<uint32_t>> wordRefs;
// fileId → [wordId1, wordId2, ...]

Обновление

wordRefs обновляется при индексации в processBatch():

// В processBatch()
auto& refv = wordRefs[batch.fileId];
if (refv.empty() || refv.back() != wid)
    refv.push_back(wid);  // Добавляем WordId в список файла
Компромисс: wordRefs занимает дополнительную память, но значительно ускоряет удаление файлов. Это классический trade-off между памятью и скоростью.

6. Сохранение и загрузка индекса

6.1. Сериализация

Проблема

Индекс нужно сохранять на диск для быстрого восстановления при перезапуске приложения.

Решение

Используется Boost.Serialization для бинарной сериализации:

// Сохранение
template<class Archive>
void save(Archive & ar, const unsigned int version) const {
    std::lock_guard<std::mutex> lock(mapMutex);
    ar & dictionary;  // Постинг-листы
    ar & wordIds;     // Словарь слов
    ar & docPaths;    // Пути к файлам
}

// Загрузка
template<class Archive>
void load(Archive & ar, const unsigned int version) {
    std::lock_guard<std::mutex> lock(mapMutex);
    ar & dictionary;
    ar & wordIds;
    ar & docPaths;
    rebuildChunksFromDictionary();  // Восстанавливаем чанки
    reconstructWordIts();           // Восстанавливаем wordRefs
}

Как это работает?

  1. Сохранение: Словарь пересобирается из чанков в плоский dictionary, затем сериализуется в бинарный файл.
  2. Загрузка: Данные загружаются из файла, затем чанки и wordRefs восстанавливаются из плоского словаря.
  3. Формат: Бинарный формат Boost.Serialization — компактный и быстрый.

6.2. rebuildDictionaryFromChunks() — пересборка словаря

Проблема

Во время работы индекс хранится в чанках для параллелизма, но для сериализации нужен плоский словарь.

Решение

void InvertedIndex::rebuildDictionaryFromChunks()
{
    std::lock_guard<std::mutex> g(mapMutex);
    dictionary.clear();
    dictionary.reserve(dictionaryChunks.size() * CHUNK_SIZE);
    
    for (const auto & chunkPtr : dictionaryChunks) {
        if (!chunkPtr) {
            // Пустой чанк = CHUNK_SIZE пустых постинг-листов
            for (size_t i=0; i<CHUNK_SIZE; ++i)
                dictionary.emplace_back();
            continue;
        }
        
        Chunk& chunk = *chunkPtr;
        std::shared_lock<std::shared_mutex> lk(chunk.mutex);
        
        // Копируем все постинг-листы из чанка
        for (size_t localIndex = 0; localIndex < CHUNK_SIZE; ++localIndex)
            dictionary.push_back(chunk.bucket[localIndex]);
    }
}
Важно: Пустые чанки создают пустые постинг-листы в словаре. Это создает "дырки" (holes), которые потом можно удалить через compact().

7. Оптимизации и обслуживание

7.1. compact() — удаление пустых постинг-листов

Проблема

После удаления файлов остаются пустые постинг-листы (holes), которые занимают место и замедляют работу.

Решение

Метод compact() удаляет пустые постинг-листы и переупорядочивает словарь:

void InvertedIndex::compact()
{
    boost::asio::post(strand_, [this]() {
        // Пересобираем dictionary из chunks
        if (dictionary.empty()) {
            rebuildDictionaryFromChunks();
        }
        
        // Подсчитываем holes
        size_t holes = 0;
        for (const auto& post : dictionary)
            if (post.empty()) ++holes;
        
        size_t dict_size = dictionary.size();
        size_t real_words = wordIds.size();
        double hole_percent = (holes * 100.0 / dict_size);
        
        // Если holes меньше 10% — не стоит compact'ить
        if (holes == 0 || holes < dict_size / 10) {
            addToLog("COMPACT: SKIP (holes < 10%)");
            return;
        }
        
        // Создаем новый словарь без holes
        std::vector<PostingList> newDict;
        newDict.reserve(dictionary.size() - holes);
        
        std::unordered_map<uint32_t, uint32_t> remap;  // oldWid → newWid
        
        for (uint32_t oldWid = 0; oldWid < dictionary.size(); ++oldWid) {
            auto& post = dictionary[oldWid];
            if (post.empty()) continue;  // Пропускаем hole
            
            auto newWid = static_cast<uint32_t>(newDict.size());
            remap[oldWid] = newWid;
            newDict.push_back(std::move(post));
            
            // Обновляем wordIds
            const std::string& word = wordIds.byId(oldWid);
            // ... пересборка wordIds с новыми ID
        }
        
        dictionary.swap(newDict);
        // Пересборка wordIds и wordRefs с новыми ID
    });
}

Как это работает?

  1. Анализ: Подсчитываются пустые постинг-листы. Если их меньше 10%, compact не выполняется.
  2. Пересборка: Создается новый словарь без пустых постинг-листов.
  3. Remap: Создается таблица перехода от старых WordId к новым.
  4. Обновление: Обновляются wordIds и wordRefs с новыми ID.
Важно: Compact выполняется в strand для безопасности, но это долгая операция. Лучше запускать её в фоновом режиме или при низкой нагрузке.

7.2. fixDictionaryHoles() — автоисправление дыр

Проблема

Иногда в индексе могут появиться "дырки" — слова, которые должны быть в файле, но отсутствуют в постингах. Это может произойти из-за ошибок или неполной индексации.

Решение

Метод fixDictionaryHoles() переиндексирует файлы для восстановления пропущенных слов:

void InvertedIndex::fixDictionaryHoles()
{
    for (FileId fileId = 0; fileId < docPaths.size(); ++fileId) {
        const std::wstring& wpath = docPaths.pathById(fileId);
        if (wpath.empty()) continue;
        
        // Читаем файл и извлекаем слова
        std::ifstream file(wpath, std::ios::binary);
        // ... токенизация и извлечение слов
        
        std::set<std::string> realWords;  // Реальные слова из файла
        
        // Проверяем, какие слова отсутствуют в индексе
        for (const std::string& word : realWords) {
            uint32_t wid;
            if (!wordIds.tryGet(word, wid)) continue;
            
            // Если слова нет в постинге — восстанавливаем
            if (!dictionary[wid].find(fileId)) {
                dictionary[wid][fileId] = 1;
                wordRefs[fileId].push_back(wid);
            }
        }
    }
}
Использование: Этот метод полезен для восстановления индекса после сбоев или для проверки целостности данных.

7.3. Статистика и мониторинг

getStats() — получение статистики

Метод getStats() возвращает подробную статистику индекса:

struct DictionaryStats {
    size_t uniqueWords;      // Реальное количество уникальных слов
    size_t totalPostings;    // Общее количество постингов
    size_t emptyPostings;    // Пустые постинг-листы (holes)
    size_t totalFiles;       // Количество файлов
    size_t memoryBytes;      // Примерный размер в памяти
};

DictionaryStats InvertedIndex::getStats() const
{
    DictionaryStats stats{};
    stats.uniqueWords = wordIds.size();  // Реальное количество слов
    stats.totalFiles = docPaths.size();
    
    // Подсчет постингов из chunks
    for (const auto& chunkPtr : dictionaryChunks) {
        if (!chunkPtr) {
            stats.emptyPostings += CHUNK_SIZE;
            continue;
        }
        
        const Chunk& chunk = *chunkPtr;
        std::shared_lock<std::shared_mutex> lk(chunk.mutex);
        
        for (const auto& posting : chunk.bucket) {
            if (posting.empty()) {
                ++stats.emptyPostings;
            } else {
                stats.totalPostings += posting.size();
                stats.memoryBytes += posting.size() * 6 + 24;  // 6 байт на постинг + overhead
            }
        }
    }
    
    return stats;
}
Использование: Статистика используется для логирования и мониторинга состояния индекса. Помогает выявить проблемы (много holes, большой размер памяти).

Типичные показатели:

Индексация:
- Скорость: 10-50 МБ/сек (зависит от CPU)

- Время поиска: < 1 мс для типичных запросов
- Масштабируемость: линейная с количеством слов

Удаление:
- Время: O(количество слов в файле)
- Обычно: < 10 мс на файл

10. Резюме

10.1. Ключевые концепции

  1. Инвертированный индекс: Слово → список документов (постинги)
  2. WordId: Компактное представление слов (экономия памяти)
  3. Chunks: Разбиение словаря для параллелизма
  4. Strand: Последовательная обработка для корректности
  5. wordRefs: Обратный индекс для быстрого удаления

10.2. Поток данных

Полный цикл индексации:

1. Сканирование → список файлов
2. Diff → новые/обновленные/удаленные
3. Удаление → через wordRefs
4. Параллельная индексация → токенизация файлов
5. Strand обработка → слова → WordId
6. Chunk commit → обновление постингов
7. Сохранение → сериализация на диск

10.3. Важные моменты

Критично для понимания:
- Strand гарантирует корректность при параллельной индексации
- Chunks обеспечивают параллелизм при обновлении постингов
- wordRefs критически важен для быстрого удаления
- dictionary используется только для сериализации, в работе — chunks
Преимущества архитектуры:
- Высокий параллелизм (до N потоков)
- Эффективное использование памяти
- Быстрый поиск и обновление
- Масштабируемость на миллионы документов
