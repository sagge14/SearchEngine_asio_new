Конспект: Как работает ASIO Server

ASIO Server — асинхронный TCP-сервер на Boost.Asio, обрабатывающий клиентские подключения и выполняющий команды (поиск, получение файлов, регистрация пользователей и др.).

1. Общая архитектура

Проблема/Контекст

Серверу поисковой системы нужно принимать множество одновременных TCP-подключений, читать команды, выполнять их (часто с тяжёлой логикой: поиск, SQL, файлы) и отправлять ответы. Блокирующий ввод-вывод ограничивает пропускную способность; нужна асинхронность.

Решение

Используется Boost.Asio с C++20 корутинами (co_await, co_spawn). Архитектура разделена на три основных класса:

┌─────────────────────────────────────────────────────────────────────────┐ │ AsioServer (принимает соединения) │ │ acceptor_ → async_accept → создаёт session для каждого клиента │ └─────────────────────────────────────────────────────────────────────────┘ │ ▼ ┌─────────────────────────────────────────────────────────────────────────┐ │ session (одно соединение): readLoop + writeLoop + commandExec │ │ - readLoop: читает Header + payload, запускает commandExec на cpu_pool │ │ - writeLoop: получает из channel и пишет в сокет │ │ - commandExec: выполняет команду и отправляет результат через channel │ └─────────────────────────────────────────────────────────────────────────┘ │ ▼ ┌─────────────────────────────────────────────────────────────────────────┐ │ Interface (статический диспетчер команд) │ │ cmdMap[COMMAND] → unique_ptr<Command> → execute(data) → vector<uint8_t> │ └─────────────────────────────────────────────────────────────────────────┘

Разбор ключевых компонентов

КомпонентНазначение
AsioServerСлушает порт, создаёт session на каждое подключение
sessionУправляет одним сокетом: чтение, запись, выполнение команд
InterfaceКарта команд → обработчики, выполнение через execCommand
write_channel_Канал для передачи данных из commandExec в writeLoop (потокобезопасно)
cpu_pool_Пул потоков для тяжёлых задач (поиск, SQL), чтобы не блокировать I/O

2. Класс AsioServer

Проблема/Контекст

Нужно принимать входящие соединения на заданном порту и для каждого создавать отдельную сессию, не блокируя основной поток.

Разбор синтаксиса

class AsioServer
{
public:
    AsioServer(
        boost::asio::io_context& net_io,   // контекст для сетевых операций
        boost::asio::thread_pool& cpu_pool, // пул для CPU-задач
        unsigned short port                 // порт прослушивания
    );

private:
    void do_accept();                      // рекурсивный вызов accept

    boost::asio::io_context& net_io_;      // ссылка на net io_context
    boost::asio::thread_pool& cpu_pool_;   // ссылка на пул потоков
    tcp::acceptor acceptor_;               // приёмник соединений
};
  • net_io_ — io_context, в котором выполняются сетевые операции (accept, read, write).
  • cpu_pool_ — thread_pool для выполнения тяжёлых команд (поиск, SQL, работа с файлами).
  • acceptor_ — TCP acceptor, слушает порт и принимает новые соединения.

Как это работает?

AsioServer::AsioServer(
    boost::asio::io_context& net_io,
    boost::asio::thread_pool& cpu_pool,
    unsigned short port
)
    : net_io_(net_io)
    , cpu_pool_(cpu_pool)
    , acceptor_(net_io_, tcp::endpoint(tcp::v4(), port))
{
    do_accept();
}

void AsioServer::do_accept() {
    acceptor_.async_accept(
        [this](boost::system::error_code ec, tcp::socket socket) {
            if (!ec)
                std::make_shared<session>(std::move(socket), cpu_pool_)->start();
            do_accept();  // сразу планируем следующий accept
        });
}
  1. В конструкторе создаётся acceptor на tcp::endpoint(tcp::v4(), port).
  2. Вызывается do_accept().
  3. async_accept асинхронно ждёт нового клиента; когда клиент подключается, вызывается callback.
  4. В callback: при отсутствии ошибки создаётся std::make_shared<session>, сокет передаётся в session, вызывается start().
  5. do_accept() вызывается снова — запускается ожидание следующего подключения (цепочка «рекурсии через callback»).
Важно: Каждое соединение обслуживается отдельным экземпляром session. Session хранится в shared_ptr, чтобы жить до завершения всех асинхронных операций.

3. Класс session

Проблема/Контекст

Для одного TCP-соединения нужно: читать данные (заголовок + payload), выполнять команду, отправлять ответ. Чтение и запись должны идти асинхронно и параллельно; выполнение команд — на отдельном пуле, чтобы не блокировать сетевой цикл.

Разбор синтаксиса

class session : public std::enable_shared_from_this<session>
{
    static constexpr std::size_t kWriteChannelCapacity = 8;  // буфер канала записи
    enum { max_length = 64 * 1024 };  // 64 KB на чтение порциями

    using WriteItem = std::variant<Header, std::shared_ptr<std::vector<BYTE>>,
                                  std::filesystem::path>;

    tcp::socket socket_;
    boost::asio::thread_pool& cpu_pool_;
    Header header_{};
    std::vector<BYTE> v_data_{};
    std::atomic_bool stopped_{false};
    std::atomic<bool> command_running_{false};  // только одна команда за раз
    boost::asio::experimental::channel<void(boost::system::error_code, WriteItem)> write_channel_;
    // ...
};
  • WriteItem — variant: может быть заголовок ответа, буфер байтов или путь к файлу (для потоковой отправки).
  • write_channel_ — канал между commandExec и writeLoop; capacity = 8 элементов.
  • command_running_ — атомарный флаг: не более одной выполняющейся команды на сессию.

Запуск сессии: start()

void session::start()
{
    auto self = shared_from_this();
    auto ex = socket_.get_executor();

    // Запуск readLoop как корутины
    boost::asio::co_spawn(ex, [self]() -> boost::asio::awaitable<void> {
        co_await self->readLoop();
    }, [self](const std::exception_ptr& eptr) {
        if (eptr) { /* логируем */ }
        self->stop("readLoop finished");
    });

    // Запуск writeLoop как корутины
    boost::asio::co_spawn(ex, [self]() -> boost::asio::awaitable<void> {
        co_await self->writeLoop();
    }, [self](const std::exception_ptr& eptr) {
        if (eptr) { /* логируем */ }
        self->stop("writeLoop finished");
    });
}

co_spawn запускает корутины в executor сокета (net_io). readLoop и writeLoop работают параллельно. При завершении любой из них (нормальном или по исключению) вызывается stop().

3.1 readLoop — цикл чтения

Как это работает?

boost::asio::awaitable<void> session::readLoop()
{
    while (!stopped_ && socket_.is_open()) {
        // 1. Читаем заголовок
        co_await boost::asio::async_read(socket_,
            boost::asio::buffer(&header_, sizeof(header_)),
            boost::asio::use_awaitable);

        // 2. Проверки: размер payload, валидность команды
        if (header_.size > MAX_PAYLOAD) { /* SOMEERROR в канал, выход */ }
        if (!trustCommand()) { /* SOMEERROR в канал, выход */ }

        // 3. Читаем payload порциями
        v_data_.assign(header_.size, 0);
        while (total_read < header_.size) {
            bytes = co_await socket_.async_read_some(...);
            total_read += bytes;
        }

        // 4. Не более одной команды одновременно
        if (command_running_.exchange(true)) {
            write_channel_.try_send(..., SERVER_BUSY_ERROR);
            return;
        }

        // 5. Запускаем commandExec на cpu_pool
        co_spawn(cpu_pool_, [self]() -> awaitable<void> {
            co_await self->commandExec();
            self->command_running_ = false;
        }, boost::asio::detached);
    }
}
  1. Читается Header (size, command).
  2. Проверяется размер payload (ограничение 1 GB) и валидность команды через trustCommand().
  3. Тело запроса читается в v_data_ порциями по 64 KB.
  4. Если уже выполняется команда, отправляется SERVER_BUSY_ERROR и цикл продолжает читать следующий запрос.
  5. Иначе commandExec запускается на cpu_pool_, чтобы не блокировать net_io.
Разделение I/O (readLoop) и CPU (commandExec на cpu_pool) позволяет обрабатывать много соединений и выполнять тяжёлые команды параллельно без блокировки сети.

3.2 writeLoop — цикл записи

Как это работает?

boost::asio::awaitable<void> session::writeLoop()
{
    while (!stopped_ && socket_.is_open()) {
        auto [ec, item] = co_await write_channel_.async_receive(
            boost::asio::as_tuple(boost::asio::use_awaitable));

        if (ec) break;  // канал закрыт

        if (auto hdr = std::get_if<Header>(&item))
            co_await boost::asio::async_write(socket_, boost::asio::buffer(hdr, sizeof(*hdr)), ...);
        else if (auto buf = std::get_if<shared_ptr<vector<BYTE>>>(&item))
            co_await boost::asio::async_write(socket_, boost::asio::buffer(**buf), ...);
        else if (auto p = std::get_if<filesystem::path>(&item))
            if (co_await openFileStream(*p))
                co_await sendNextFileChunk();  // потоковая отправка файла
    }
}

writeLoop ждёт элементы из write_channel_. В зависимости от типа WriteItem:

  • Header — пишет заголовок в сокет.
  • shared_ptr<vector<BYTE>> — пишет буфер.
  • filesystem::path — открывает файл и потоково отправляет через sendNextFileChunk (chunk 64 KB).

3.3 commandExec — выполнение команды

Как это работает?

boost::asio::awaitable<void> session::commandExec()
{
    // Обработка специальных команд
    if (header_.command == COMMAND::SOMEERROR) {
        write_channel_.try_send(..., header_);
        co_return;
    }

    if (header_.command == COMMAND::GETBINFILE) {
        // Путь к файлу в v_data_
        std::string pathStr(v_data_.begin(), v_data_.end());
        if (!exists(file_path)) {
            write_channel_.try_send(..., SOMEERROR);
            co_return;
        }
        header_.size = file_size(file_path);
        co_await write_channel_.async_send(..., header_, ...);
        co_await write_channel_.async_send(..., file_path, ...);  // потоковая отправка
        // ...
    }
    else {
        // Обычные команды через Interface
        if (header_.command == COMMAND::USER_REGISTRY)
            userName_ = string(v_data_.begin(), v_data_.end());
        else
            answer = Interface::execCommand(header_.command, v_data_);

        header_.size = answer.size();
        co_await write_channel_.async_send(..., header_, ...);
        co_await write_channel_.async_send(..., make_shared<vector<BYTE>>(answer), ...);
    }
    logutil::log(personalRequest);
}

Команда выполняется, результат уходит в write_channel_, откуда его забирает writeLoop.

3.4 stop() — завершение сессии

void session::stop(const char* why)
{
    if (stopped_.exchange(true)) return;  // идемпотентно

    write_channel_.close();   // writeLoop выйдет из async_receive
    socket_.shutdown(...);
    socket_.close(ec);
    logutil::log(userName_, "EMPTY", "DISCONNECT");
}

Закрытие канала прерывает ожидание writeLoop, затем закрывается сокет.

4. Протокол: Header и COMMAND

Структура сообщения

struct Header {
    uint_fast64_t size{};   // размер payload в байтах
    COMMAND command{};      // код команды
};

Каждое сообщение: [Header 16 байт][Payload size байт].

Список команд (enum COMMAND)

Команды задаются макросом COMMAND_LIST (SOLOREQUEST, FILETEXT, GETBINFILE, PING и т.д.). Специальная команда SAVE_MESSAGE_TO кодируется в старших 32 битах (userId).

trustCommand() — валидация

bool session::trustCommand() {
    if (header_.command > SOMEERROR && header_.command < END_COMMAND)
        return true;
    if ((uint64_t)header_.command >> 32 == SAVE_MESSAGE_TO) {
        userId_ = (uint32_t)(header_.command & 0xFFFFFFFF);
        header_.command = COMMAND::SAVE_MESSAGE_TO;
        Interface::setCommand(SAVE_MESSAGE_TO, make_unique<SaveMessageCmd>(userId_));
        return true;
    }
    header_.command = SOMEERROR;
    return false;
}

Проверяется диапазон команды или специальный формат SAVE_MESSAGE_TO с userId в младших 32 битах.

5. Interface — диспетчер команд

Проблема/Контекст

Команд много (поиск, файлы, SQL, регистрация, пинг и т.д.). Нужен единый механизм: по коду команды вызывать соответствующий обработчик.

Решение

class Interface {
    inline static std::string year_{};
    inline static SearchServer* searchServer_ = nullptr;
    inline static std::map<COMMAND, std::unique_ptr<Command>> cmdMap{};

public:
    static void setYear(const std::string& year);
    static void setSearchServer(SearchServer* _server);
    static void setCommand(COMMAND command, std::unique_ptr<Command> myCmd);
    static std::vector<uint8_t> execCommand(COMMAND _command, std::vector<uint8_t>& _request);
};

cmdMap — карта «команда → обработчик». В setSearchServer заполняются команды: 

// Пример из setSearchServer:
cmdMap[COMMAND::SOLOREQUEST] = std::make_unique<SoloRequestCmd>(searchServer_);
cmdMap[COMMAND::PING] = std::make_unique<PingCmd>();
cmdMap[COMMAND::GET_OPIS_BASE] = std::make_unique<GetFileCmd>([](auto){ return "D:\\OPIS_ADMIN\\" + year_ + ".db"; });
// ...

execCommand вызывает cmdMap.at(_command)->execute(_request) и возвращает vector<uint8_t>.

Command — интерфейс с методом virtual std::vector<uint8_t> execute(const std::vector<uint8_t>& data). Каждая команда реализует свой обработчик.

6. Инициализация в main.cpp

// 1. Настройка Interface
asio_server::Interface::setYear(settings.year);
asio_server::Interface::setSearchServer(&server);  // заполняет cmdMap

// 2. Создание AsioServer
auto asioServer = std::make_shared<asio_server::AsioServer>(
    runtime.net(),      // io_context для сети
    runtime.cpu_pool(), // thread_pool для команд
    settings.port       // порт
);

runtime предоставляет net() (io_context) и cpu_pool(). AsioServer запускает do_accept и начинает принимать соединения.

7. Диаграмма потока данных

Клиент session cpu_pool_ │ │ │ │ ─── [Header+Payload] ──>│ readLoop │ │ │ │ │ │ │ └──> co_spawn(commandExec) ─────────>│ commandExec │ │ │ │ │ │ │ │ write_channel_.async_send│ │ │ │ └──────────────────────────┼─────┘ │ │ │ │ │ writeLoop <── async_receive(channel) │ │ │ │ │ │ <── [Header+Answer] ───│ async_write(socket) │ │ │ │

8. Ключевые моменты для запоминания

  • AsioServer — acceptor + создание session на каждое соединение.
  • session — readLoop + writeLoop (параллельно) + commandExec на cpu_pool.
  • write_channel_ — связь между commandExec и writeLoop (вариант: Header, буфер, путь к файлу).
  • Interface — cmdMap и execCommand для диспетчеризации команд.
  • Протокол — Header (size, command) + payload; trustCommand проверяет валидность.
В одной сессии одновременно выполняется не более одной команды (command_running_). При повторном запросе до завершения предыдущего возвращается SERVER_BUSY_ERROR.
