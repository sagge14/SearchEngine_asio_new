# Полный синтетический стенд архивации

`SearchEngineArchiveE2EStand` создаёт одноразовый набор данных для проверки
индексации, заморозки, переноса и возврата SearchEngine. Генератор не копирует
записи из рабочих архивов. Из рабочих `ARCHIVE.db3` использована только форма
таблицы `ARCHIVE` для PRM и PRD.

## Состав

Для заданного года создаются:

- 12 баз `autopad/PRM/METH_BASES/MM-YYYY.db3`;
- 12 баз `autopad/PRD/METH_BASES/MM-YYYY.db3`;
- не менее 10 синтетических телеграмм в каждой базе;
- для PRM — 12 каталогов с исходными именами месячных `index_roots` из
  переданного `Settings.json` (например, `content/ЯНВАРЬ`);
- для PRD — единый каталог `content/TLG` для исходящих телеграмм и ZIP с
  приложениями;
- уникальный текст, номер и контрольный код в каждом основном файле; поля
  `CODE = значение` и `DIGITAL = значение` содержат пробелы с обеих сторон
  знака `=`, чтобы код и значение индексировались отдельными словами;
- 0, 1 или 2 приложения к телеграмме;
- прямые файлы приложений PRM и штатные ZIP-контейнеры приложений PRD;
- `production/F12/YYYY.db` с актуальной схемой `way` версии 4 и одной
  синтетической записью выдачи для каждой телеграммы: `type=1` для PRM и
  `type=2` для PRD; `way.number` совпадает с `ARCHIVE.Index` соответствующей
  месячной базы, как при штатном поиске F12 в AutoPad;
- `server/data/Settings.json` с абсолютными путями только внутрь стенда;

Искусственная иерархия `content/autopad/PRM/2026/PRM-01` не создаётся.
Каталоги `autopad/PRM` и `autopad/PRD` содержат только раздельные месячные
SQLite-базы и не дублируются внутри `content`.

Живая операционная база `ARCHIVE.db3` намеренно не создаётся и не переносится.
Стенд проверяет работу только с месячными базами и позволяет обнаружить
нежелательную попытку сервера создать отсутствующую `ARCHIVE.db3`.

Публикация атомарная: сначала строится скрытый staging-каталог, выполняются
`PRAGMA integrity_check`, проверка схем, строк, путей, файлов, ZIP и размеров
приложений, после чего каталог переименовывается в итоговый. Уже существующий
итоговый каталог генератор не перезаписывает.

## Отдельная цель сборки

Генератор не входит в обычную сборку и релиз `SearchEngineService`:
`BUILD_ARCHIVE_E2E_STAND_TOOL` по умолчанию выключен, а штатные упаковщики
сервера не копируют `SearchEngineArchiveE2EStand.exe`. Для него предусмотрен
отдельный Windows 7 x86 preset и отдельная версия продукта.

```powershell
. .\scripts\AppVersion.ps1
Sync-SearchEngineAppVersion -ProjectRoot $PWD `
  -ProductName SearchEngineArchiveE2EStand
cmake --preset windows7-x86-archive-e2e-stand
cmake --build --preset windows7-x86-archive-e2e-stand-release `
  --target SearchEngineArchiveE2EStand
```

Для разработки вместе с тестами можно явно включить цель в обычном Win32
дереве, но это не меняет состав серверного пакета:

```powershell
cmake --preset windows-x86 -DBUILD_TESTS=ON -DBUILD_ARCHIVE_E2E_STAND_TOOL=ON
cmake --build --preset windows-x86-debug `
  --target SearchEngineArchiveE2EStand ArchiveE2EStand_test
```

## Отдельный релиз стенда

Каноническая версия генератора хранится независимо в
`app-version.SearchEngineArchiveE2EStand.json`. Полный стенд выпускается только
явным скриптом и использует уже готовый переносимый пакет
`SearchEngineService-x86-Windows7` как источник бинарников, настроек и
установочных файлов:

```powershell
.\scripts\Build-SearchEngineArchiveE2EStandRelease.ps1 `
  -ServicePackageDirectory `
    .\out\package\0.1.69\SearchEngineService-x86-Windows7 `
  -Year 2026
```

Исходный серверный пакет должен быть свежим, неотредактированным и собранным
для того же `-Year`. Перед выпуском скрипт проверяет защищённые файлы по
`package-manifest.json`, а изменяемый `data\Settings.json` — сравнением с
заново сформированным каноническим шаблоном выбранного года. Поэтому случайно
положить в stand-релиз рабочие настройки нельзя.

Скрипт выполняет отдельный version bump генератора, собирает только цель
`SearchEngineArchiveE2EStand`, проверяет хэши исходного серверного пакета,
создаёт и дважды проверяет v3, а затем записывает
`stand-release.json` и `stand-release-checksums.sha256`. Локальный результат
появляется в
`out\package\<версия-генератора>\<имя-службы>-<год>`.
Канонический выпуск требует чистое Git-дерево и записывает SHA исходного
коммита. `-AllowDirtySource` разрешён только для одноразового локального
smoke-теста и явно отмечается в `stand-release.json`.

Если настроен `WORKSPACE_RELEASE_CLOUD_ROOT`, дополнительно публикуются ZIP и
SHA-256 в отдельный продукт `SearchEngineArchiveE2EStand`; ключ
`-SkipCloudPublish` оставляет только локальный результат. Обычные релизы
`SearchEngineService`, `BackupService`, `BackupRestore` и `ZagEditor` этот
стенд не собирают и не публикуют.

ZIP сохраняет внешний каталог `<имя-службы>-<год>`, поэтому его можно
распаковать непосредственно в корень выбранного диска данных. Запускать
`Deploy-Workstation-Stand.bat` нужно из этого каталога; раскладывать его файлы
по одному прямо в корень диска не требуется.

## Создание и повторная проверка

```powershell
out\build\windows-x86\Debug\SearchEngineArchiveE2EStand.exe generate `
  --root D:\SearchEngine-E2E\stand-2026 `
  --settings-template deployment\SearchEngineServicePortable\source-data\Settings.json `
  --year 2026 --records 10

out\build\windows-x86\Debug\SearchEngineArchiveE2EStand.exe verify `
  --root D:\SearchEngine-E2E\stand-2026
```

Путь `--root` должен отсутствовать. Для повторной генерации следует указать
новый пустой путь; автоматического удаления старого стенда нет.

## Архивный стенд v3 для штатного BAT

Команда `generate-service-archive` создаёт не исходный набор для последующей
архивации, а уже замороженную копию службы в формате существующего
`SearchEngineArchive.exe`. В корне присутствуют оба разных манифеста:

- `archive-operation.json` — формат 1 операции `service-archive`, который читает
  `Archive-SearchEngineService.bat`;
- `stand-manifest.json` — паспорт и контрольные данные генератора стенда.

В v3 также входят переносимый `SearchEngine.exe` с DLL, валидный синтетический
`inverted_index.sqlite`, 24 месячные базы, файлы телеграмм, скрипт регистрации
одноразовой службы и русская инструкция. Рабочие данные не читаются.

Имя итогового каталога обязано быть `<service-name>-<year>`. Родительский
каталог и диск выбирать можно свободно. Физический `--root`, куда генератор
пишет результат, может отличаться от шаблонного `--deployment-root`; их
конечное имя должно совпадать. `--restore-root` задаёт только имя будущего
каталога возврата: при подготовке он будет размещён рядом с фактическим
архивным стендом.

```powershell
out\build\windows-x86\Debug\SearchEngineArchiveE2EStand.exe `
  generate-service-archive `
  --root D:\Build\SearchEngineService-StandV3-2026 `
  --deployment-root D:\123\SearchEngineService-StandV3-2026 `
  --restore-root D:\123\restored-service-stand-2026-v3 `
  --program-template D:\Package\app `
  --preparer-template D:\BuildWin7\SearchEngineArchiveE2EStand.exe `
  --installer-template D:\Package `
  --settings-template D:\Package\data\Settings.json `
  --service-name SearchEngineService-StandV3 `
  --port 25027 --year 2026 --records 10
```

На ВМ каталог можно распаковать на любой диск и в любой родительский каталог,
но нельзя переименовывать сам `<service-name>-<year>`. Администратор запускает
`Activate-Archived-Stand.bat`. Он сначала вызывает Win7 x86 preparer из
`tools`, повторяемо перепривязывает оба JSON, `inverted_index.sqlite` и 24 поля
`DirectTo` месячных баз к фактическому пути, а затем регистрирует службу.
После этого в существующем
`Archive-SearchEngineService.bat` выбирает `2`, затем `2` и указывает именно
корень v3. После выбора архива утилита предлагает два способа разморозки:

1. Вернуть в записанные исходные места 1:1. Этот вариант используется для
   архива, созданного после `Deploy-Workstation-Stand.bat`: программа
   возвращается в `Program Files`, данные — в `ProgramData`, а TLG и базы —
   в исходные каталоги выбранного рабочего тома.
2. Восстановить всё под выбранный каталог. Это прежний переносимый режим;
   после его выбора можно ввести `D:`, `D:\`, `D:\StandV3` или выбрать каталог
   в окне.

В режиме 1 используются только пути, записанные при заморозке в
`archive-operation.json`; `F12` и `OPIS_ADMIN` не входят в эти пути и не
затрагиваются. В режиме 2 сам выбранный корень не обязан быть пустым, но
конкретные цели `program`, `data`, `content` и `autopad` должны отсутствовать.
Существующие файлы не перезаписываются.
При первом испытании архив после восстановления удалять не следует.

### Дополнительная раскладка чистой VM

Если при генерации указан `--installer-template`, стенд дополнительно содержит
полную переносимую установочную папку и отдельный
`Deploy-Workstation-Stand.bat`. Существующие
`Activate-Archived-Stand.bat`, `Prepare-Archived-Stand.bat` и восстановление в
выбранный единый каталог не меняются.

Новый BAT запускается администратором только на одноразовой чистой VM. Он
устанавливает приложенный Visual C++ Runtime, просит букву тома, выполняет
полную проверку отсутствия целевых каталогов и создаёт раскладку установщика:

- `%ProgramFiles(x86)%\<service>\bin` — сервер и runtime DLL;
- `%ProgramFiles(x86)%\<service>\tools` — штатные служебные утилиты;
- `%ProgramData%\<service>` — `Settings.json`, SQLite-индекс, служебные данные
  и `logs`;
- в корне выбранного тома — 12 каталогов месяцев, `TLG`, `BASES`,
  `BASES_PRD`, `OPIS_ADMIN` и `F12`; в `F12` копируется годовая база
  `YYYY.db` с тестовой историей выдачи всех телеграмм стенда;
- месячные SQLite-базы — в `BASES\METH_BASES` и
  `BASES_PRD\METH_BASES`.

После копирования helper переписывает `Settings.json`, `docs.path` поискового
индекса и `DirectTo` всех 24 месячных баз на фактические пути, повторно
проверяет SQLite и только затем BAT регистрирует тестовую службу, правило
firewall, запускает сервер и выполняет health-проверку.

Если служба уже существует, развёртывание прекращается. Конечные каталоги
стенда могут отсутствовать либо уже существовать пустыми: это относится к
каталогам программы и данных службы, 12 месячным каталогам, `TLG`,
`BASES\METH_BASES`, `BASES_PRD\METH_BASES`, `OPIS_ADMIN` и `F12`.
Родительские `BASES` и `BASES_PRD` могут содержать другие данные — deploy
проверяет и заполняет только их каталоги `METH_BASES`, не изменяя соседние
файлы. Непустой конечный каталог, файл вместо каталога или reparse point
считается конфликтом до начала копирования. Файлы никогда не заменяются.
При ошибке удаляются только файлы и каталоги, созданные текущим deploy;
существовавшие до запуска пустые каталоги сохраняются. Автоматические тесты
проверяют этот режим только на подменённых временных `Program Files`,
`ProgramData` и корне тома; SCM и системные каталоги тестами не изменяются.

## Автоматические проверки

Набор `ArchiveE2EStand.*` проверяет:

1. полную генерацию и повторную верификацию 24 SQLite-баз и 240 телеграмм;
2. обнаружение повреждённого размера приложения;
3. реальный годовой перенос всех файлов и месячных баз, исправление `DirectTo`,
   публикацию манифеста и доказуемое удаление источников;
4. сохранение исходной декабрьской PRD-базы согласно специальному правилу;
5. построение восстановления под выбранным корневым каталогом и отказ до
   копирования, если там уже существует любой каталог назначения;
6. генерацию v3 с legacy-совместимым `archive-operation.json`, рабочим SQLite-
   индексом и исполняемым шаблоном;
7. переносимую и повторяемую перепривязку JSON/SQLite к фактическому каталогу,
   а также отсутствие ошибочно экранированных `^>nul` и `^|` в BAT;
8. актуальную схему и версию годовой базы F12, совпадение `way.number` с
   `ARCHIVE.Index`, связь всех строк `way` с телеграммами месячных баз, типы
   PRM/PRD и целостность SQLite;
9. дополнительную раскладку чистой VM на подменённые корни, включая 13
   индексных каталогов, 24 месячные базы, `F12/YYYY.db`, штатные
   `Program Files`/`ProgramData` и отказ при любой коллизии.
10. формат индексируемых полей `CODE = значение` и `DIGITAL = значение`, а
    также отказ верификатора при слитном написании вокруг `=`.

```powershell
out\build\windows-x86\Debug\ArchiveE2EStand_test.exe `
  --gtest_filter=ArchiveE2EStand.*
```

Установка тестовой Windows-службы в автоматические проверки не входит. Её
делает только явный запуск `Activate-Archived-Stand.bat` администратором на
одноразовой ВМ. Генератор и тесты не меняют SCM, рабочие службы и рабочие
каталоги.
