# SearchEngine — HANDOFF: аудит команд и работы в режиме Windows-службы

## Назначение документа

Этот handoff фиксирует проблемы и спорные места, обнаруженные при проверке того,
как переход от ручного запуска `SearchEngine.exe` из каталога на диске `D:` к
основному режиму установки как Windows-службы влияет на выполнение сетевых
команд, файловые пути, настройки, индекс, авторизацию и обновление сервера.

Документ является **реестром решений**, а не заданием исправить всё сразу.
Каждый пункт должен разбираться отдельно. По результату обсуждения пункт можно:

- принять к исправлению;
- изменить;
- отложить;
- признать допустимым поведением;
- отменить;
- закрыть после реализации и проверки.

Не объединять все пункты в один большой рефакторинг. Для каждого принятого
решения сначала зафиксировать ожидаемое поведение, затем выполнять узкое
изменение и отдельную проверку.

## Модель статусов

Для каждого пункта использовать один статус:

```text
OPEN       — проблема зафиксирована, решение не принято
ANALYSIS   — идёт отдельный разбор вариантов
DECIDED    — решение принято и записано в пункте
DEFERRED   — осознанно отложено
REJECTED   — исправление не требуется, текущее поведение принято
CANCELLED  — пункт отменён
IN_PROGRESS — выполняется реализация
FIXED      — код изменён, но итоговая проверка ещё не завершена
VERIFIED   — решение реализовано и проверено
```

В каждом пункте перед реализацией заполнить:

```text
Статус:
Решение:
Причина решения:
Ветка/коммит:
Проверка:
```

# Подробные пункты

## SVC-001 — runtime-root службы отличается от старого каталога программы

**Приоритет:** P1  
**Статус:** OPEN

### Подтверждённое поведение

Установщик регистрирует службу примерно так:

```text
%ProgramFiles%\SearchEngineService\bin\SearchEngine.exe
    --service
    --service-name SearchEngineService
    --data-dir %ProgramData%\SearchEngineService
```

При старте сервер устанавливает `data-dir` текущим каталогом процесса. Поэтому
в service mode относительные runtime-пути относятся к:

```text
%ProgramData%\SearchEngineService
```

а не к каталогу EXE и не к прежней рабочей папке на `D:`.

Основные runtime-файлы:

```text
Settings.json
OEM866.INI
inverted_index.sqlite
log.db
server_log.log
logs\
messages\
auth_clients.sqlite
issuer-public.pem        (если ключ размещён рядом с сервером)
prefix_map.json          (если legacy GET_ATTACHMENTS используется)
```

Пользователь, который раньше менял `Settings.json` и вспомогательные файлы рядом
с EXE, теперь может по ошибке менять неиспользуемую копию в старом каталоге или
в `Program Files`.

Изменение `Settings.json` не является hot reload: для применения требуется
перезапуск службы.

### Риск

- оператор меняет не тот файл;
- настройки визуально изменены, но служба продолжает работать по старым;
- обычный пользователь может не иметь прав записи в `%ProgramData%`;
- выдавать `Users: Modify` на весь data-dir опасно, потому что там находятся
  auth DB, индекс и служебное состояние.

### Варианты решения

1. Оставить текущую модель, но явно документировать путь и штатный процесс
   `stop -> edit/validate -> start`.
2. Добавить административный helper для просмотра/редактирования/валидации
   установленного экземпляра.
3. Разделить data-dir на зоны, например:

```text
config\
state\
logs\
```

   и выдавать оператору права только на `config`.
4. Добавить безопасную команду reload только после отдельного анализа того,
   какие настройки допустимо менять без полной пересборки runtime.

### Критерии приёмки

- оператор однозначно видит активный путь настроек;
- невозможно случайно отредактировать неиспользуемую копию;
- права на auth DB и индекс не расширяются ради редактирования настроек;
- способ применения изменений явно определён и проверен.

## SVC-002 — служба работает не в пользовательской сессии

**Приоритет:** P0/P1  
**Статус:** OPEN

### Подтверждённое поведение

`sc create` не задаёт `obj=`, поэтому служба по умолчанию запускается как
`LocalSystem`.

Служба не наследует пользовательскую сессию и обычно не видит:

- mapped drives, созданные через Explorer или `net use` конкретного
  пользователя;
- пользовательский `subst`;
- ресурсы, требующие пользовательских сетевых credentials;
- тома, которые появляются только после интерактивного входа/разблокировки.

Локальный физический диск `D:` обычно виден, если ACL разрешают доступ.

### Затронуто

- индексирование `config.dirs`;
- file watchers;
- PRM/PRD базы;
- F12 и OPIS базы;
- `GETBINFILE` / `FILETEXT`;
- `GET_TELEGA_ATACHMENTS` / `GET_SINGLE_ATACHMENT`;
- `GET_OPIS_BASE`;
- `LOAD_TLG_TO_SEND` / `LOAD_RAZN`;
- `GET_ATTACHMENTS` и удаление его буфера.

### Риск

Сервер может успешно перейти в `RUNNING` и отвечать на `PING`, но не читать
рабочие каталоги или не иметь права записывать файлы.

### Варианты решения

1. Официально поддерживать только локальные диски и проверять это установщиком.
2. Для сетевых источников использовать UNC и отдельную service account с
   минимальными правами.
3. Добавить настройку service account в установку.
4. Добавить preflight-проверку чтения/записи каждого обязательного root от имени
   той же учётной записи, под которой будет работать служба.
5. Настроить зависимости/отложенный запуск только как дополнительную меру;
   delayed-auto сам по себе не гарантирует готовность пользовательского или
   сетевого ресурса.

### Критерии приёмки

- документирован поддерживаемый тип хранилища;
- установщик или отдельный diagnostic показывает service account;
- обязательные каталоги проверены именно в service context;
- сетевые пути не зависят от пользовательских букв дисков.

## SVC-003 — clean install не обеспечивает `GET_ATTACHMENTS`

**Приоритет:** P0, если команда нужна в эксплуатации  
**Статус:** OPEN

### Подтверждённое поведение

`GetAttachmentsCmd` по умолчанию открывает относительный файл:

```text
prefix_map.json
```

В service mode это означает:

```text
%ProgramData%\SearchEngineService\prefix_map.json
```

Portable `source-data` на текущем HEAD содержит только:

```text
Settings.json
ignore.txt
OEM866.INI.base64 -> OEM866.INI
```

`prefix_map.json` в пакет и data-dir не устанавливается.

### Следствие

После чистой установки `GET_ATTACHMENTS` возвращает configuration error, пока
оператор вручную не создаст/не скопирует корректный `prefix_map.json` в активный
data-dir.

Это не относится к обычному скачиванию приложений выбранного документа через
`GETBINFILE`; это отдельный legacy-механизм получения операторского буфера.

### Варианты решения

1. Команда нужна: добавить явный runtime path, шаблон/импорт, package validation
   и installer UX.
2. Команда нужна только на части серверов: сделать опциональную конфигурацию с
   явным статусом `disabled`, а не общей configuration error.
3. Команда больше не нужна: убрать её из UI/обработки, сохранив wire ordinal как
   reserved/legacy, если это требуется для совместимости.
4. Заменить механизм другим endpoint после отдельного согласования семантики.

### Критерии приёмки

- после clean install заранее известно, включена команда или отключена;
- включённая команда работает без ручного копирования скрытого файла;
- выключенная команда возвращает понятный детерминированный результат;
- переустановка не теряет пользовательскую конфигурацию.

## SVC-004 — legacy-семантика `GET_ATTACHMENTS` требует отдельного решения

**Приоритет:** P1/P2  
**Статус:** OPEN

### Подтверждённое поведение

Команда:

1. получает имя оператора;
2. находит каталог через `prefix_map.json`;
3. рекурсивно читает все файлы;
4. сериализует их в один ответ;
5. после успешного чтения удаляет весь исходный каталог буфера.

Клиент вызывает `GET_ATTACHMENTS` только на `primaryServerId()`.

### Вопросы, которые нельзя решать автоматически

- удаление буфера после чтения остаётся обязательной бизнес-семантикой или это
  исторический побочный эффект;
- что делать при обрыве после удаления каталога, но до полного получения ответа
  клиентом;
- может ли буфер находиться на дополнительном сервере;
- должен ли клиент опрашивать все серверы или только назначенный основной;
- допустим ли один большой сериализованный ответ для крупного буфера;
- нужны ли подтверждение получения, повторная доставка или quarantine.

### Возможные решения

- оставить legacy-поведение без изменений и только обеспечить конфиг;
- выдавать без удаления;
- удалять после отдельного ACK;
- перемещать в processed/quarantine;
- заменить на list + download + acknowledge;
- полностью отменить сценарий.

### Критерии приёмки

Сначала письменно зафиксирована бизнес-семантика. Только после этого менять код.

## SVC-005 — повторная установка теряет активное runtime-состояние

**Приоритет:** P0  
**Статус:** OPEN

### Подтверждённое поведение установщика

При reinstall/update:

1. считываются старые значения `Settings.json` для диалога;
2. служба останавливается;
3. старый `INSTALL_ROOT` перемещается в rollback-каталог;
4. старый `%ProgramData%\<service>` целиком перемещается в rollback-каталог;
5. создаётся новый пустой data-dir;
6. туда копируется `data\*` из пакета и новый `Settings.json`;
7. запускается служба;
8. выполняется только health `PING/PONG`;
9. rollback-каталоги удаляются после успешного `PING/PONG`.

Старое runtime-состояние не возвращается в новый data-dir автоматически.
Внешний backup, если выбран, является экспортом, но не автоматическим
продолжением работы новой установки.

### Под угрозой

```text
auth_clients.sqlite
issuer-public.pem, если лежит в data-dir
inverted_index.sqlite
inverted_index.sqlite-wal / -shm
messages\
prefix_map.json
пользовательский ignore.txt
log.db
server_log.log
logs\
другие добавленные оператором runtime-файлы
```

Особенно критично после перехода на USB/PC auth tokens: новая пустая
`auth_clients.sqlite` может успешно открыться, `PING` пройдёт, но все ранее
зарегистрированные клиенты перестанут авторизоваться.

### Требуемое решение

Разделить:

```text
immutable application files
mutable configuration
persistent state
rebuildable cache/index
logs
```

Обновление бинарников не должно по умолчанию заменять persistent data-dir.
Для каждого файла определить политику:

- сохранить как есть;
- мигрировать;
- пересоздать;
- импортировать только по явному решению;
- удалить только при full uninstall.

### Минимальные требования

- `auth_clients.sqlite` сохраняется при обычном update;
- ключ проверки сохраняется или гарантированно разрешается из стабильного
  keystore;
- `prefix_map.json` сохраняется, если функция включена;
- index либо сохраняется, либо переиндексация явно объявляется до запуска;
- rollback проверяет не только `PING`, но и доступность persistent state;
- полное удаление данных выполняется только через явно выбранный uninstall/reset.

### Критерии приёмки

Проверить сценарий:

1. установить службу;
2. зарегистрировать USB и PC clients;
3. создать индекс и test message/state;
4. выполнить update тем же instance name;
5. убедиться, что старые клиенты авторизуются;
6. убедиться, что индекс/настройки/опциональные конфиги имеют ожидаемую
   политику сохранения;
7. смоделировать неудачный запуск новой версии и проверить rollback.

## SVC-006 — `PING/PONG` не является достаточным health-check

**Приоритет:** P0/P1  
**Статус:** OPEN

### Подтверждённое поведение

После установки служба считается исправной, если:

- SCM сообщает `RUNNING`;
- сервер отвечает на `PING`.

`PING` является bootstrap-командой и не проверяет пользовательскую
авторизацию или рабочие источники данных.

### Что может быть сломано при успешном `PING`

- `auth_clients.sqlite` создана заново и пуста;
- отсутствует `prefix_map.json`;
- `D:` или AutoPad-каталоги недоступны;
- OPIS/F12 базы недоступны;
- индекс пуст или перестраивается не из тех каталогов;
- служба не может читать приложение по `DirectTo`;
- служба не может записывать `LOAD_TLG_TO_SEND`/`LOAD_RAZN`;
- service account не имеет нужных ACL.

### Варианты решения

1. Оставить `PING` как liveness, добавить отдельный readiness/diagnostic.
2. Добавить installer smoke-check с выбранным профилем обязательных функций.
3. Добавить `DIAGNOSTICS_V1`, возвращающий структурированный статус без выдачи
   секретных путей обычному клиенту.
4. Проверять auth DB schema/count, index open, configured roots, AutoPad roots,
   optional feature configs и write probes.

### Критерии приёмки

- liveness и readiness различаются;
- installer не удаляет rollback, пока обязательный профиль не прошёл;
- optional функции не блокируют установку, если они явно disabled;
- diagnostic сообщает конкретную причину, а не только `health failed`.

## SVC-007 — недоступный root может быть принят за пустой каталог

**Приоритет:** P0  
**Статус:** OPEN

### Подтверждённое поведение

`FileScanner` при ошибке открытия root записывает ошибку и возвращает пустой
результат для этого каталога.

Полный update затем сравнивает общий список найденных файлов с каталогом
документов. Исчезнувшие пути не удаляются физически из индекса, но помечаются
`deleted` по модели «вечного следа».

### Опасный сценарий

1. Windows загружается.
2. Служба delayed-auto стартует до появления `D:`/тома/сети.
3. `scan_on_startup=true` запускает scan.
4. root недоступен и даёт ноль файлов.
5. ранее известные документы помечаются удалёнными.
6. сервер уже может принимать запросы.
7. позже ресурс появляется; следующий scan реактивирует и переиндексирует файлы,
   но до этого система показывает массово удалённое/неполное состояние.

Проблема также возникает при `Access denied`, временном сетевом сбое или ошибке
родительского каталога.

### Требуемое разделение состояний

Scanner должен различать:

```text
AVAILABLE_EMPTY
AVAILABLE_WITH_FILES
UNAVAILABLE
ACCESS_DENIED
PARTIAL_SCAN
```

Нельзя публиковать destructive diff как достоверный, если обязательный root не
был успешно просканирован.

### Варианты решения

- abort всего full update при недоступном обязательном root;
- применить diff только по успешно просканированным roots, сохранив остальные;

## SVC-008 — watcher после появления родителя может не подхватить существующие дети

**Приоритет:** P1  
**Статус:** OPEN

### Подтверждённое поведение

`MultiDirWatcher` при старте создаёт inner watcher для существующих настроенных
подкаталогов. Если parent недоступен, поток периодически пытается открыть parent.
После успешного открытия он ждёт события изменения имён каталогов.

Не подтверждено, что после позднего появления parent выполняется повторное
перечисление всех уже существующих `kids`. Если каталог уже существует к моменту
успешного открытия parent, новое событие `ADDED/RENAMED_NEW_NAME` может не прийти.

### Следствие

Периодический full scan позже может восстановить индекс, но оперативные события
из каталога не будут поступать до перезапуска службы или нового directory event.

### Варианты решения

- вынести `ensureExistingChildrenWatched()` и вызывать при каждом успешном
  открытии/reopen parent;
- периодически сверять `kids_` и `inner_`;
- после восстановления parent запускать controlled scan;
- добавить watcher state в diagnostics.

### Критерии приёмки

Интеграционный тест:

1. запустить watcher с отсутствующим parent;
2. создать parent и заранее все configured child directories;
3. не создавать дополнительных directory events;
4. изменить файл внутри child;
5. событие должно быть принято без перезапуска процесса.

## SVC-009 — `GETBINFILE` и `FILETEXT` не ограничены рабочими корнями

**Приоритет:** P0 security  
**Статус:** OPEN

### Подтверждённое поведение

Команды принимают путь от авторизованного клиента и проверяют в основном:

- непустой путь;
- отсутствие NUL;
- существование;
- regular file/open/read.

Canonical allowlist разрешённых серверных roots не применяется.

В service mode процесс обычно работает как `LocalSystem`. Поэтому область
доступного чтения существенно шире, чем при старом запуске от обычного
пользователя.

### Риск

Компрометация одного client token, ошибка выдачи прав или дефект клиента даёт
возможность запросить не только поисковый документ, но потенциально любой файл,
который может прочитать service account.

Auth gate снижает вероятность внешнего доступа, но не заменяет ограничение
объектов, которые команда вправе читать.

### Варианты решения

1. Для `GETBINFILE`/`FILETEXT` ввести canonical allowlist roots.
2. Разделить command capabilities по назначению.
3. Передавать document/attachment ID, а путь разрешать только на сервере.
4. Для приложений использовать scoped endpoint `GET_SINGLE_ATACHMENT`.
5. Оставить raw path endpoint только для localhost/admin diagnostic, если он
   действительно нужен.
6. Запустить службу под ограниченной account как defense in depth.

### Обязательные проверки пути

- absolute/canonical normalization;
- запрет выхода через `..`;
- обработка symlink/junction/reparse point;
- проверка нахождения final path под разрешённым root;
- запрет чтения самого data-dir/auth DB/ключей, если endpoint не предназначен
  для этого;
- TOCTOU-анализ при open.

### Критерии приёмки

- разрешённый документ скачивается;
- путь вне roots отклоняется typed error;
- `..`, другой drive, UNC и reparse escape не обходят ограничение;
- поведение согласовано с клиентом без перенумерации существующих wire IDs.

## SVC-012 — основной клиент использует универсальный `GETBINFILE` для приложений

**Приоритет:** P1  
**Статус:** OPEN

### Подтверждённое поведение клиента

Команды `GET_PRIL` в текущем wire-контракте нет.

При обычном сохранении результата клиент строит для входящего документа:

```text
outputName = имя из PrilName
remotePath = parent(DirectTo/FileName) + имя приложения
command = GETBINFILE
```

Для исходящего документа клиент строит полный путь к `<num>.zip` и также
скачивает его как файл.

Поэтому сам новый current working directory службы этот основной сценарий не
ломает: клиент передаёт абсолютный путь из данных сервера. Он ломается только,
если путь неверен или service account не может его прочитать.

### Почему пункт всё равно открыт

На сервере уже существуют более узкие команды:

```text
GET_TELEGA_ATACHMENTS
GET_SINGLE_ATACHMENT
```

Они получают `id/type`, читают `PrilName/DirectTo` на сервере, проверяют, что
запрошенное имя объявлено у телеграммы, и не принимают произвольный полный путь
от клиента.

### Варианты решения

1. Оставить текущий `GETBINFILE`, исправив allowlist из SVC-009.
2. Перевести UI приложений на list + single attachment.
3. Использовать scoped команды для AutoPad, а `GETBINFILE` оставить только для
   обычного текста найденного документа.
4. Спроектировать единый document-file endpoint с server-side ID.

### Ограничения

Это двухрепозиторное изменение. Не менять ordinal существующих команд. Сервер и
клиент должны обновляться согласованно с fallback на период развёртывания.

### Критерии приёмки

- входящие и исходящие приложения скачиваются;
- multi-server source routing сохраняется;
- отсутствует передача произвольного пути там, где достаточно ID;
- missing/deleted attachment выдаёт понятный typed error;
- старые клиенты не ломаются без принятого compatibility plan.

## SVC-013 — legacy-state и диагностические сообщения службы

**Приоритет:** P2  
**Статус:** OPEN

### Подтверждённое поведение

`MessageQueue` использует:

```text
current_path() / messages
```

Благодаря установке CWD в data-dir это попадает в правильный `%ProgramData%`
каталог. Само по себе это сейчас не ошибка, но зависимость неявная.

### Вопросы

- message endpoints ещё используются или должны остаться только wire legacy;
- нужна ли долговечная очередь после restart/update;
- нужно ли удалять сообщение после успешного чтения;
- должен ли `GET_MESSAGE` использовать реальную authenticated identity;
- можно ли удалить `users.dat`/`RegisterUserCmd` из runtime, сохранив wire
  compatibility;
- какие `cout/cerr` должны быть переведены в structured logs.

### Варианты решения

- оставить legacy и только исправить логирование/persistence;
- пометить endpoints disabled/deprecated;
- заменить на нормальную authenticated queue;
- удалить недостижимый внутренний код без изменения wire ordinal.

### Критерии приёмки

- по каждому legacy endpoint принято явное решение;

## SVC-014 — список имён команд шире реально поддерживаемого request registry

**Приоритет:** P2  
**Статус:** OPEN

### Подтверждённое поведение

В `COMMAND_LIST` остаются исторические имена, для которых нет разрешения в

```text
JSONREGUEST
ADDRESOLUTION
UPDATE
GETRESOLUTIONS
GETRESOLUTION
GETDOCS
GETDOC
```

Если старый клиент отправит такую команду, сервер отклонит её как invalid

1. Оставить ordinals, но явно назвать/документировать их reserved/unsupported.
2. Перевести enum на явные числовые значения для всех элементов, затем аккуратно

# Подтверждённые выводы, которые не следует ошибочно считать поломкой

1. Console mode и service mode создают один `SearchEngineApplication` и один
   набор command handlers. Отдельной урезанной «service-версии команд» нет.
2. Основной клиентский download приложения через `GETBINFILE` передаёт полный
   путь. Смена CWD сама по себе его не ломает.
3. `GET_TELEGA_ATACHMENTS` и `GET_SINGLE_ATACHMENT` получают путь через AutoPad
   данные на сервере и не зависят от каталога EXE.
4. `MessageQueue` с относительным `messages` сейчас попадает в data-dir, потому
   что startup явно меняет CWD.
5. Команды `GET_PRIL` в текущем контракте нет. Под похожим названием обычно
   подразумевается либо `GETBINFILE`, либо scoped attachment commands, либо
   legacy `GET_ATTACHMENTS`.
6. Для локального физического `D:` service mode обычно работает при корректных
   ACL. Основной риск SVC-002 относится к mapped/network/late-mounted ресурсам и
   ограниченным ACL.

# Правила реализации будущих решений

- Перед кодом обновить поле `Решение` соответствующего пункта.
