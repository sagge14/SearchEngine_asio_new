# Экономная история `mirror_history`

Режим дополняет, а не заменяет полные независимые снимки `snapshot`.

## Структура

Для цели `D:\BASES_PRD` каталог хранения выглядит примерно так:

```text
F:\AutoPadEconomicalBackups\
  BASES_PRD_<идентификатор>\
    current\
      manifest.json
      data\
        ARCHIVE.db3
        PARAMETERS.db3
        METH_BASES\
          02-2026.db3
    objects\
      by-path\
        ARCHIVE.db3\
          4f19...c821
          a372...091d
        METH_BASES\
          02-2026.db3\
            91a0...e62c
    restore_points\
      every_1min\
        20260730_120000\
          manifest.json
        20260730_120100\
          manifest.json
      every_1h\
        20260730_120000\
          manifest.json
      every_1mo\
        20260701_000000\
          manifest.json
```

`current\data` — готовая последняя копия. При изменении `ARCHIVE.db3` старая
версия атомарно переносится в `objects`, а новая занимает её место в
`current\data`. Остальные файлы не переписываются.

Каждая историческая точка — только манифест со списком относительных путей,
размеров и SHA-256. Нужный файл берётся:

1. из `current\data`, если его SHA-256 совпадает с манифестом;
2. иначе из `objects\by-path\<относительный путь>\<sha256>`.

Одинаковая версия файла физически хранится один раз. После ротации точек
неиспользуемые объекты удаляются автоматически.

## Исключения `exclude`

Для каталожных целей можно задать необязательный массив шаблонов:

```json
"exclude": [
  "__astcache/",
  ".vs/",
  "out/",
  "*.obj",
  "*.tmp",
  "Thumbs.db"
]
```

Правила gitignore-подобные, относительно корня `src`. Встроенных исключений
нет. `.git`, `*.exe`, `*.dll`, `*.pdb` и `*.log` не отфильтровываются сами по
себе: широкие маски нужно добавлять осознанно.

Исключённый каталог отсекается целиком при обходе источника, поэтому
недоступное или постоянно меняющееся содержимое внутри него не делает проход
неполным и не создаёт новую точку. Изменение только исключённых путей даёт
`Unchanged`.

После добавления правила исключённые файлы исчезают из `current/data` и
`current/manifest.json`. Старые restore point остаются восстанавливаемыми:
нужные объекты хранятся, пока на них есть ссылки, а существующий garbage
collection удаляет их после истечения retention.

В новые манифесты записывается фактически применённый массив `"exclude"`
(формат остаётся `1`, поле необязательное для старых читателей).
`BackupRestore` это поле игнорирует и восстанавливает ровно содержимое
выбранного манифеста.

## Ошибки отдельного файла

Проход сначала обновляет все файлы, которые удалось корректно снять. Для
неудачного файла сохраняется предыдущая рабочая версия. `current\manifest.json`
получает `complete: false` и список ошибок, а новые restore point за этот
проход не публикуются. Следующий проход повторит неудачные файлы.

Для SQLite в режиме `auto` используется Online Backup API и проверка
целостности. Временные `-journal`, `-wal` и `-shm` не входят в зеркало.

## Ручное восстановление

Последнее состояние восстанавливается копированием всего `current\data` в
новый пустой каталог. Перед заменой рабочих баз нужно остановить приложения и
отключить сетевых пользователей.

Историческое состояние вручную собирать можно по алгоритму выше, но безопаснее
использовать утилиту `BackupRestore` (см. `docs/BACKUP_RESTORE_UTILITY_PROPOSAL.md`):

```text
BackupRestore targets --root F:\AutoPadEconomicalBackups
BackupRestore points  --root F:\AutoPadEconomicalBackups --target BASES
BackupRestore restore --root F:\AutoPadEconomicalBackups --target BASES --latest --to D:\Recovered\BASES
```
