R: Управление ресурсами - Подробный конспект

О разделе: Раздел R содержит рекомендации по управлению ресурсами (память, файлы, блокировки и т.д.). Правильное управление ресурсами предотвращает утечки и делает код безопасным.

R.1: Управляйте ресурсами автоматически, используя дескрипторы ресурсов и RAII

Проблема/Контекст

Ручное управление ресурсами (выделение/освобождение памяти, открытие/закрытие файлов) подвержено ошибкам. Легко забыть освободить ресурс или освободить его дважды. RAII автоматизирует управление ресурсами.

RAII (Resource Acquisition Is Initialization): Ресурс приобретается в конструкторе и освобождается в деструкторе. Это гарантирует автоматическое освобождение ресурса при выходе из области видимости.

❌ Как НЕ надо

// Плохо: ручное управление ресурсами
void process_file(const char* filename) {
    FILE* file = fopen(filename, "r");
    if (!file) return;  // утечка, если файл не открыт
    
    char buffer[100];
    if (fgets(buffer, sizeof(buffer), file) == nullptr) {
        fclose(file);  // нужно не забыть
        return;
    }
    
    // обработка...
    
    if (error) {
        return;  // УТЕЧКА! файл не закрыт
    }
    
    fclose(file);  // легко забыть
}

// Плохо: ручное управление памятью
void allocate_data() {
    int* data = new int[1000];
    // ... использование ...
    if (error) {
        return;  // УТЕЧКА памяти!
    }
    delete[] data;  // легко забыть
}

// Плохо: ручное управление блокировкой
std::mutex mtx;
void critical_section() {
    mtx.lock();
    // ... работа ...
    if (error) {
        return;  // блокировка не снята!
    }
    mtx.unlock();  // легко забыть
}

✅ Как надо

// Хорошо: RAII для файлов
#include <fstream>
void process_file(const std::string& filename) {
    std::ifstream file(filename);
    if (!file.is_open()) {
        return;  // автоматически закроется при выходе
    }
    
    std::string line;
    if (!std::getline(file, line)) {
        return;  // автоматически закроется
    }
    
    // обработка...
    
    if (error) {
        return;  // автоматически закроется
    }
    // файл автоматически закроется при выходе
}

// Хорошо: умные указатели для памяти
#include <memory>
void allocate_data() {
    auto data = std::make_unique<int[]>(1000);
    // ... использование ...
    if (error) {
        return;  // память автоматически освободится
    }
    // память автоматически освободится при выходе
}

// Хорошо: lock_guard для блокировок
#include <mutex>
std::mutex mtx;
void critical_section() {
    std::lock_guard<std::mutex> lock(mtx);
    // ... работа ...
    if (error) {
        return;  // блокировка автоматически снимется
    }
    // блокировка автоматически снимется при выходе
}

R.3: Сырой указатель (T*) не владеет

Проблема/Контекст

Сырые указатели не выражают владение. Неясно, кто отвечает за удаление объекта. Это приводит к утечкам памяти или двойному удалению.

❌ Как НЕ надо

// Плохо: сырой указатель для владения
int* create_data() {
    int* ptr = new int{42};
    return ptr;  // кто удалит? Неясно!
}

void use_data() {
    int* data = create_data();
    // ... использование ...
    // Кто удаляет data? Неизвестно!
    // delete data;  // может быть ошибкой, если владелец другой
}

// Плохо: неясное владение
void process(int* data) {
    // data принадлежит функции? Или просто используется?
    // нужно ли удалять data?
}

✅ Как надо

// Хорошо: unique_ptr для владения
#include <memory>
std::unique_ptr<int> create_data() {
    return std::make_unique<int>(42);  // явное владение
}

void use_data() {
    auto data = create_data();  // владение передано
    // ... использование ...
    // data автоматически удалится при выходе
}

// Хорошо: ссылка для невладеющего доступа
void process(const int& data) {
    // функция не владеет data, просто использует
    // data должен существовать вне функции
}

// Хорошо: observer_ptr для невладеющих указателей
template<typename T>
using observer_ptr = T*;  // указатель без владения

void observe(observer_ptr<const int> data) {
    // функция наблюдает за data, но не владеет им
}

R.5: Предпочитайте объекты с ограниченной областью видимости

Проблема/Контекст

Выделение памяти в куче дороже, чем размещение на стеке. Объекты на стеке автоматически уничтожаются при выходе из области видимости, что упрощает управление ресурсами.

❌ Как НЕ надо

// Плохо: ненужное выделение в куче
void process(int n) {
    auto obj = new MyClass{n};  // выделение в куче
    // ... использование ...
    delete obj;  // нужно не забыть удалить
}

// Плохо: выделение для маленьких объектов
void calculate() {
    auto result = new int{0};  // зачем в куче?
    *result = 42;
    delete result;
}

✅ Как надо

// Хорошо: объект на стеке
void process(int n) {
    MyClass obj{n};  // на стеке, автоматически уничтожится
    // ... использование ...
    // автоматическое уничтожение
}

// Хорошо: локальная переменная
void calculate() {
    int result = 0;  // на стеке
    result = 42;
    // автоматическое уничтожение
}

// Хорошо: vector вместо массива в куче
void process_data() {
    std::vector<int> data(1000);  // на стеке (управляет памятью)
    // ... использование ...
    // автоматическое освобождение памяти
}

R.20: Используйте unique_ptr или shared_ptr для представления владения

Проблема/Контекст

Когда нужно выделить память в куче, используйте умные указатели вместо сырых указателей. Они автоматически управляют временем жизни объекта.

❌ Как НЕ надо

// Плохо: сырой указатель для владения
void create_and_use() {
    int* ptr = new int{42};
    // ... использование ...
    delete ptr;  // легко забыть
}

// Плохо: неясное владение
class Container {
    int* data;  // кто владеет?
public:
    Container(int* d) : data(d) {}  // принимаем владение?
    ~Container() {
        delete data;  // или просто используем?
    }
};

✅ Как надо

// Хорошо: unique_ptr для единоличного владения
#include <memory>
void create_and_use() {
    auto ptr = std::make_unique<int>(42);
    // ... использование ...
    // автоматическое удаление
}

// Хорошо: явное владение через unique_ptr
class Container {
    std::unique_ptr<int> data;  // явное владение
public:
    explicit Container(std::unique_ptr<int> d) 
        : data(std::move(d)) {}  // принимаем владение
    // автоматическое удаление в деструкторе
};

// Хорошо: shared_ptr для разделяемого владения
std::shared_ptr<int> create_shared() {
    return std::make_shared<int>(42);
}

void use_shared(std::shared_ptr<int> ptr) {
    // разделяемое владение
    // объект удалится, когда последний shared_ptr уничтожится
}

R.21: Предпочитайте unique_ptr над shared_ptr, если вам не нужно разделять владение

Проблема/Контекст

unique_ptr проще и быстрее, чем shared_ptr. Используйте shared_ptr только когда действительно нужно разделять владение между несколькими объектами.

❌ Как НЕ надо

// Плохо: shared_ptr когда не нужно разделять владение
void process() {
    auto ptr = std::make_shared<int>(42);  // зачем shared?
    // только один владелец
    // ...
}

// Плохо: shared_ptr для единоличного владения
class Owner {
    std::shared_ptr<Resource> resource;  // только один владелец
public:
    Owner() : resource(std::make_shared<Resource>()) {}
};

✅ Как надо

// Хорошо: unique_ptr для единоличного владения
void process() {
    auto ptr = std::make_unique<int>(42);  // единоличное владение
    // быстрее и проще
    // ...
}

// Хорошо: unique_ptr для единоличного владения
class Owner {
    std::unique_ptr<Resource> resource;  // единоличное владение
public:
    Owner() : resource(std::make_unique<Resource>()) {}
};

// Хорошо: shared_ptr только когда нужно разделять владение
class SharedOwner1 {
    std::shared_ptr<Resource> resource;
public:
    SharedOwner1(std::shared_ptr<Resource> r) : resource(r) {}
};

class SharedOwner2 {
    std::shared_ptr<Resource> resource;
public:
    SharedOwner2(std::shared_ptr<Resource> r) : resource(r) {}
};

// Использование:
auto resource = std::make_shared<Resource>();
SharedOwner1 owner1(resource);  // разделяемое владение
SharedOwner2 owner2(resource);  // разделяемое владение
// Resource удалится, когда оба owner уничтожатся

R.22: Используйте make_shared() для создания shared_ptr

Проблема/Контекст

make_shared более эффективен, чем создание shared_ptr через new, потому что он может выделить память для объекта и счётчика ссылок одним блоком.

❌ Как НЕ надо

// Плохо: создание через new
std::shared_ptr<int> ptr(new int{42});  // два выделения памяти

// Плохо: небезопасно при исключениях
void unsafe_create() {
    process(std::shared_ptr<int>(new int{42}), 
            std::shared_ptr<int>(new int{43}));
    // если второй new выбросит исключение,
    // первый объект утечёт!
}

✅ Как надо

// Хорошо: make_shared
auto ptr = std::make_shared<int>(42);  // одно выделение памяти

// Хорошо: безопасно при исключениях
void safe_create() {
    process(std::make_shared<int>(42),
            std::make_shared<int>(43));
    // безопасно даже при исключениях
}

R.23: Используйте make_unique() для создания unique_ptr

Проблема/Контекст

make_unique более безопасен и читаем, чем создание unique_ptr через new. Он также обеспечивает безопасность исключений.

❌ Как НЕ надо

// Плохо: создание через new
std::unique_ptr<int> ptr(new int{42});  // повторение типа

// Плохо: небезопасно при исключениях
void unsafe_create() {
    process(std::unique_ptr<int>(new int{42}),
            std::unique_ptr<int>(new int{43}));
    // если второй new выбросит исключение,
    // первый объект утечёт!
}

✅ Как надо

// Хорошо: make_unique
auto ptr = std::make_unique<int>(42);  // без повторения типа

// Хорошо: безопасно при исключениях
void safe_create() {
    process(std::make_unique<int>(42),
            std::make_unique<int>(43));
    // безопасно даже при исключениях
}

Заключение

Ключевые принципы раздела R (Управление ресурсами):

  • RAII: Используйте RAII для автоматического управления ресурсами
  • Умные указатели: Используйте unique_ptr и shared_ptr вместо сырых указателей
  • Стек вместо кучи: Предпочитайте объекты на стеке выделению в куче
  • make_* функции: Используйте make_unique и make_shared для создания умных указателей
  • Явное владение: Используйте типы для выражения владения ресурсами
Правило: Если вы используете new, подумайте, можно ли использовать умный указатель или объект на стеке. Ручное управление ресурсами должно быть исключением, а не правилом.
