C: Классы и иерархии классов - Подробный конспект

О разделе: Раздел C содержит рекомендации по проектированию классов и иерархий классов. Правильное использование классов делает код более модульным, безопасным и понятным.

C.1: Организуйте связанные данные в структуры (struct или class)

Проблема/Контекст

Когда данные логически связаны, их следует группировать вместе. Это делает код более понятным и предотвращает ошибки при передаче параметров.

❌ Как НЕ надо

// Плохо: неявные связи между параметрами
void draw_rectangle(int x1, int y1, int x2, int y2);
void set_user_info(int id, int age, int salary);

// Легко перепутать порядок:
draw_rectangle(10, 20, 30, 40);  // что есть что?
set_user_info(25, 30, 50000);    // правильно?

✅ Как надо

// Хорошо: явные связи через структуры
struct Point { int x, y; };
struct Rectangle { Point top_left, bottom_right; };
void draw_rectangle(const Rectangle& rect);

struct UserInfo { int id, age, salary; };
void set_user_info(const UserInfo& info);

// Использование:
Rectangle rect{{10, 20}, {30, 40}};
draw_rectangle(rect);  // понятно!

UserInfo user{25, 30, 50000};
set_user_info(user);  // невозможно перепутать

C.2: Используйте class, если класс имеет инвариант; используйте struct, если члены данных могут изменяться независимо

Проблема/Контекст

Инвариант класса - это условие, которое всегда должно быть истинным для валидного объекта класса. Если класс имеет инвариант, используйте class с приватными членами. Если члены могут изменяться независимо, используйте struct.

❌ Как НЕ надо

// Плохо: struct с инвариантом
struct Date {
    int year, month, day;  // все публичные
};

Date d{2024, 13, 32};  // невалидная дата, но компилятор не знает

// Плохо: class без инварианта
class Pair {
private:
    std::string name;  // зачем приватность?
    int volume;        // если они независимы?
public:
    void set_name(const std::string& n) { name = n; }
    void set_volume(int v) { volume = v; }
};

✅ Как надо

// Хорошо: struct для независимых данных
struct Pair {
    std::string name;   // могут изменяться независимо
    int volume;
};

Pair p{"item", 10};
p.name = "new_item";    // ОК
p.volume = 20;          // ОК

// Хорошо: class для данных с инвариантом
class Date {
    int year, month, day;  // приватные для поддержания инварианта
public:
    Date(int y, int m, int d) {
        if (m < 1 || m > 12 || d < 1 || d > 31) {
            throw std::invalid_argument("Invalid date");
        }
        year = y; month = m; day = d;
    }
    // методы для безопасного доступа
};

Date d{2024, 12, 25};  // валидная дата

C.20: Если можете избежать определения операций по умолчанию, делайте это

Проблема/Контекст

Компилятор автоматически генерирует конструктор копирования, оператор присваивания, конструктор перемещения, оператор перемещения и деструктор, если они не определены. Если поведение по умолчанию подходит, не определяйте их явно.

Правило нуля: Если все члены класса имеют все специальные функции, дальнейшая работа не нужна.

❌ Как НЕ надо

// Плохо: ненужное определение операций
class MyClass {
    std::string name;
    int value;
public:
    MyClass() = default;
    MyClass(const MyClass& other) : name(other.name), value(other.value) {}
    MyClass& operator=(const MyClass& other) {
        name = other.name;
        value = other.value;
        return *this;
    }
    ~MyClass() {}  // пустой деструктор
};

✅ Как надо

// Хорошо: компилятор сгенерирует всё автоматически
class MyClass {
    std::string name;  // имеет все операции
    int value;         // имеет все операции
public:
    // ничего не нужно определять!
    // Компилятор сгенерирует:
    // - конструктор по умолчанию
    // - конструктор копирования
    // - оператор присваивания
    // - конструктор перемещения
    // - оператор перемещения
    // - деструктор
};

C.21: Правило пяти

Проблема/Контекст

Если вы определяете одну из специальных функций (деструктор, конструктор копирования, оператор присваивания, конструктор перемещения, оператор перемещения), вы должны определить или удалить все пять.

Правило пяти: Если вы определяете одну из этих операций, определите или =delete все пять.

❌ Как НЕ надо

// Плохо: определён только деструктор
class Resource {
    int* data;
public:
    Resource() : data(new int[100]) {}
    ~Resource() { delete[] data; }  // определён деструктор
    // но конструктор копирования и оператор присваивания
    // сгенерированы компилятором - ОПАСНО!
};

Resource r1;
Resource r2 = r1;  // копирование указателя!
// При уничтожении - двойное удаление!

✅ Как надо

// Хорошо: определён деструктор, удалены операции копирования
class Resource {
    int* data;
public:
    Resource() : data(new int[100]) {}
    ~Resource() { delete[] data; }
    
    // Удаляем копирование (или определяем правильно)
    Resource(const Resource&) = delete;
    Resource& operator=(const Resource&) = delete;
    
    // Разрешаем перемещение
    Resource(Resource&& other) noexcept : data(other.data) {
        other.data = nullptr;
    }
    Resource& operator=(Resource&& other) noexcept {
        if (this != &other) {
            delete[] data;
            data = other.data;
            other.data = nullptr;
        }
        return *this;
    }
};

// Или используем умный указатель (правило нуля)
class ResourceGood {
    std::unique_ptr<int[]> data;  // автоматическое управление
public:
    ResourceGood() : data(std::make_unique<int[]>(100)) {}
    // всё остальное сгенерировано автоматически!
};

C.30: Определите деструктор, если классу нужно явное действие при уничтожении объекта

Проблема/Контекст

Деструктор вызывается автоматически при уничтожении объекта. Если нужно освободить ресурсы или выполнить другую очистку, определите деструктор.

❌ Как НЕ надо

// Плохо: ресурс не освобождается
class FileHandler {
    FILE* file;
public:
    FileHandler(const char* name) {
        file = fopen(name, "r");
    }
    // нет деструктора - утечка файлового дескриптора!
};

// Плохо: ненужный деструктор
class SimpleData {
    int value;
public:
    SimpleData(int v) : value(v) {}
    ~SimpleData() {}  // пустой деструктор не нужен
};

✅ Как надо

// Хорошо: деструктор освобождает ресурс
class FileHandler {
    FILE* file;
public:
    FileHandler(const char* name) {
        file = fopen(name, "r");
        if (!file) throw std::runtime_error("Cannot open file");
    }
    ~FileHandler() {
        if (file) {
            fclose(file);  // освобождаем ресурс
        }
    }
};

// Хорошо: используем RAII (std::fstream)
#include <fstream>
class FileHandlerGood {
    std::ifstream file;  // автоматически закрывается
public:
    FileHandlerGood(const std::string& name) : file(name) {
        if (!file.is_open()) {
            throw std::runtime_error("Cannot open file");
        }
    }
    // деструктор не нужен - std::ifstream сам закроет файл
};

// Хорошо: простой класс без деструктора
class SimpleData {
    int value;
public:
    SimpleData(int v) : value(v) {}
    // деструктор по умолчанию достаточен
};

C.42: Если конструктор не может создать валидный объект, выбросьте исключение

Проблема/Контекст

Конструктор должен создавать валидный объект. Если это невозможно, лучше выбросить исключение, чем создать невалидный объект.

❌ Как НЕ надо

// Плохо: невалидный объект
class Date {
    int year, month, day;
public:
    Date(int y, int m, int d) {
        year = y;
        month = m;  // может быть 13!
        day = d;    // может быть 32!
    }
    bool is_valid() const {
        return month >= 1 && month <= 12 && day >= 1 && day <= 31;
    }
};

Date d{2024, 13, 32};  // создан невалидный объект
if (!d.is_valid()) {  // нужно проверять вручную
    // ...
}

✅ Как надо

// Хорошо: конструктор гарантирует валидность
class Date {
    int year, month, day;
public:
    Date(int y, int m, int d) {
        if (m < 1 || m > 12) {
            throw std::invalid_argument("Invalid month");
        }
        if (d < 1 || d > 31) {
            throw std::invalid_argument("Invalid day");
        }
        year = y;
        month = m;
        day = d;
    }
    // объект всегда валиден после конструктора
};

try {
    Date d{2024, 12, 25};  // валидная дата
    // можно использовать без проверок
} catch (const std::invalid_argument& e) {
    // обработали ошибку
}

C.10: Предпочитайте конкретные типы иерархиям классов

Проблема/Контекст

Конкретные типы (без виртуальных функций) проще, быстрее и понятнее, чем типы в иерархии классов. Используйте иерархии только когда нужен полиморфизм.

❌ Как НЕ надо

// Плохо: ненужная иерархия
class Shape {
public:
    virtual ~Shape() = default;
    virtual double area() const = 0;
};

class Circle : public Shape {
    double radius;
public:
    Circle(double r) : radius(r) {}
    double area() const override {
        return 3.14159 * radius * radius;
    }
};

// Использование только одного типа - зачем иерархия?
Circle c{5.0};
double a = c.area();

✅ Как надо

// Хорошо: конкретный тип
class Circle {
    double radius;
public:
    explicit Circle(double r) : radius(r) {
        if (r < 0) throw std::invalid_argument("Radius must be positive");
    }
    double area() const {
        return 3.14159 * radius * radius;
    }
    double get_radius() const { return radius; }
};

// Использование:
Circle c{5.0};
double a = c.area();  // быстрее, проще

// Иерархия нужна только для полиморфизма:
std::vector<std::unique_ptr<Shape>> shapes;
shapes.push_back(std::make_unique<Circle>(5.0));
shapes.push_back(std::make_unique<Rectangle>(3.0, 4.0));
for (auto& shape : shapes) {
    std::cout << shape->area() << "\n";  // полиморфизм
}

Заключение

Ключевые принципы раздела C (Классы):

  • Группировка данных: Связанные данные должны быть в структурах
  • class vs struct: Используйте class для инвариантов, struct для независимых данных
  • Правило нуля: Если можете избежать определения операций, делайте это
  • Правило пяти: Если определяете одну операцию, определите все пять
  • Валидные объекты: Конструктор должен создавать валидный объект
  • Конкретные типы: Предпочитайте конкретные типы иерархиям
