C++ Core Guidelines - Конспект

О документе: C++ Core Guidelines — это набор рекомендаций по написанию современного C++ кода, разработанный Bjarne Stroustrup и Herb Sutter. Документ помогает писать более безопасный, эффективный и поддерживаемый код.

Содержание

  • P: Философия
  • I: Интерфейсы
  • F: Функции
  • C: Классы и иерархии классов
  • R: Управление ресурсами
  • ES: Выражения и операторы
  • Per: Производительность
  • CP: Параллелизм
  • E: Обработка ошибок
  • Con: Константы и неизменяемость
  • T: Шаблоны и обобщённое программирование

P: Философия

Основные принципы

P.1: Выражайте идеи напрямую в коде

Причина: Компиляторы не читают комментарии. То, что выражено в коде, имеет определённую семантику и может быть проверено компилятором и инструментами.

// Плохо: неясно, что возвращается
int month();  

// Хорошо: явно указан тип возврата и константность
Month month() const;

P.2: Пишите на стандартном ISO C++

Причина: Это набор рекомендаций для написания стандартного ISO C++.

Внимание: Используйте современный компилятор C++ (C++20 или C++17) с опциями, которые не принимают расширения.

P.3: Выражайте намерения

Причина: Если намерение кода не указано, невозможно понять, делает ли код то, что должен.

// Плохо: неясно намерение
gsl::index i = 0;
while (i < v.size()) {
    // ... работа с v[i] ...
}

// Хорошо: явно выражено намерение пройти по элементам
for (const auto& x : v) { 
    /* работа со значением x */ 
}

P.4: В идеале программа должна быть статически типобезопасной

Причина: Статическая типобезопасность предотвращает множество ошибок на этапе компиляции.

Проблемные области: union, приведения типов, распад массивов, ошибки диапазона, сужающие преобразования.

P.5: Предпочитайте проверки на этапе компиляции проверкам во время выполнения

Причина: Ясность кода и производительность. Вам не нужно писать обработчики ошибок для ошибок, пойманных на этапе компиляции.

// Плохо: проверка во время выполнения
int bits = 0;
for (Int i = 1; i; i <<= 1)
    ++bits;
if (bits < 32)
    cerr << "Int слишком мал\n";

// Хорошо: проверка на этапе компиляции
static_assert(sizeof(Int) >= 4);  // проверка на этапе компиляции

P.8: Не допускайте утечек ресурсов

Причина: Даже медленный рост ресурсов со временем исчерпает их доступность.

// Плохо: возможна утечка файлового дескриптора
void f(const char* name)
{
    FILE* input = fopen(name, "r");
    // ...
    if (something) return;   // плохо: утечка дескриптора
    // ...
    fclose(input);
}

// Хорошо: RAII автоматически закрывает файл
void f(const char* name)
{
    ifstream input {name};
    // ...
    if (something) return;   // ОК: нет утечки
    // ...
}

I: Интерфейсы

Основные правила для интерфейсов

I.1: Делайте интерфейсы явными

Причина: Правильность. Предположения, не указанные в интерфейсе, легко упустить и сложно протестировать.

// Плохо: неявная зависимость от глобальной переменной
int round(double d)
{
    return (round_up) ? ceil(d) : d;  // неочевидная зависимость
}

// Хорошо: явный параметр
int round(double d, bool round_up)
{
    return round_up ? ceil(d) : d;
}

I.2: Избегайте неконстантных глобальных переменных

Причина: Неконстантные глобальные переменные скрывают зависимости и делают их подверженными непредсказуемым изменениям.

Важно: Инициализация глобальных объектов не полностью упорядочена. Если вы используете глобальный объект, инициализируйте его константой.

I.4: Делайте интерфейсы точно и строго типизированными

Причина: Типы — это простейшая и лучшая документация, улучшают читаемость и проверяются на этапе компиляции.

// Плохо: что означают числа?
draw_rect(100, 200, 100, 500);

// Хорошо: явные типы
void draw_rectangle(Point top_left, Point bottom_right);
void draw_rectangle(Point top_left, Size height_width);

draw_rectangle(p, Point{10, 20});  // два угла
draw_rectangle(p, Size{10, 20});    // угол и размер

I.10: Используйте исключения для сигнализации о невозможности выполнить требуемую задачу

Причина: Невозможно игнорировать исключение. Это может привести к неверным результатам или неопределённому состоянию системы.

// Плохо: возврат отрицательного числа при ошибке
int printf(const char* ...);  

// Хорошо: исключение при ошибке
template<class F, class ...Args>
explicit thread(F&& f, Args&&... args);  // выбрасывает system_error

I.11: Никогда не передавайте владение через сырой указатель (T*) или ссылку (T&)

Причина: Если есть сомнения относительно того, кто владеет объектом, произойдут утечки или преждевременное уничтожение.

// Плохо: кто удаляет возвращённый X?
X* compute(args)
{
    X* res = new X{};
    // ...
    return res;
}

// Хорошо: возврат по значению (используется move semantics)
vector<double> compute(args)
{
    vector<double> res(10000);
    // ...
    return res;
}

F: Функции

Определение функций

F.1: "Упаковывайте" осмысленные операции в тщательно названные функции

Причина: Вынесение общего кода делает код более читаемым, более вероятным для повторного использования и ограничивает ошибки от сложного кода.

F.2: Функция должна выполнять одну логическую операцию

Причина: Функция, выполняющая одну операцию, проще для понимания, тестирования и повторного использования.

// Плохо: монолит
void read_and_print()
{
    int x;
    cin >> x;
    // проверка ошибок
    cout << x << "\n";
}

// Хорошо: разделение на логические части
int read(istream& is)
{
    int x;
    is >> x;
    // проверка ошибок
    return x;
}

void print(ostream& os, int x)
{
    os << x << "\n";
}

F.3: Держите функции короткими и простыми

Причина: Большие функции сложно читать, более склонны содержать сложный код и более склонны иметь переменные в больших, чем минимальные, областях видимости.

Правило: "Не помещается на экран" часто является хорошим практическим определением "слишком большой". Функции от одной до пяти строк должны считаться нормальными.

F.6: Если ваша функция не должна выбрасывать исключения, объявите её noexcept

Причина: Если исключение не должно выбрасываться, программа не может справиться с ошибкой и должна быть завершена как можно скорее. Объявление функции noexcept помогает оптимизаторам.

// Хорошо: деструктор не должен выбрасывать исключения
class X {
public:
    ~X() noexcept;
    // ...
};

Передача параметров

F.16: Для "входных" параметров передавайте дешёвые для копирования типы по значению, остальные — по ссылке на const

Причина: Оба способа дают вызывающему знать, что функция не будет изменять аргумент.

void f1(const string& s);  // ОК: передача по ссылке на const; всегда дёшево
void f2(string s);         // плохо: потенциально дорого
void f3(int x);            // ОК: непревзойдённо
void f4(const int& x);     // плохо: накладные расходы на доступ

F.17: Для "входно-выходных" параметров передавайте по ссылке на неконстанту

Причина: Это делает очевидным для вызывающих, что объект предполагается изменяемым.

void update(Record& r);  // предполагается, что update записывает в r

F.20: Для "выходных" значений предпочитайте возвращаемые значения выходным параметрам

Причина: Возвращаемое значение самодокументируемо, тогда как & может быть либо входно-выходным, либо только выходным.

// ОК: возврат указателей на элементы со значением x
vector<const int*> find_all(const vector<int>&, int x);

// Плохо: размещение указателей в выходном параметре
void find_all(const vector<int>&, vector<const int*>& out, int x);

C: Классы и иерархии классов

Основные правила

C.1: Организуйте связанные данные в структуры (struct или class)

Причина: Упрощение понимания. Если данные связаны (по фундаментальным причинам), этот факт должен отражаться в коде.

// Плохо: неявные связи
void draw(int x, int y, int x2, int y2);

// Хорошо: явные связи
void draw(Point from, Point to);

C.2: Используйте class, если класс имеет инвариант; используйте struct, если члены данных могут изменяться независимо

Причина: Читаемость. Использование class предупреждает программиста о необходимости инварианта.

// struct: члены могут изменяться независимо
struct Pair {
    string name;
    int volume;
};

// class: есть инвариант (валидная дата)
class Date {
public:
    Date(int yy, Month mm, char dd);
    // ...
private:
    int y;
    Month m;
    char d;
};

C.9: Минимизируйте открытость членов

Причина: Инкапсуляция. Сокрытие информации. Минимизация шанса непреднамеренного доступа.

Примечание: Предпочитайте порядок: public члены перед protected членами перед private членами.

Конкретные типы

C.10: Предпочитайте конкретные типы иерархиям классов

Причина: Конкретный тип принципиально проще типа в иерархии классов: проще проектировать, реализовывать, использовать, рассуждать о нём, он меньше и быстрее.

// Конкретный тип: можно разместить на стеке
class Point1 {
    int x, y;
    // ... операции ...
    // ... нет виртуальных функций ...
};

// Использование
Point1 p11 {1, 2};   // создание объекта на стеке
Point1 p12 {p11};    // копия

Конструкторы, присваивания и деструкторы

C.20: Если можете избежать определения операций по умолчанию, делайте это

Причина: Это самое простое и даёт самую чистую семантику.

struct Named_map {
public:
    explicit Named_map(const string& n) : name(n) {}
    // нет конструкторов копирования/перемещения
    // нет операторов присваивания
    // нет деструктора
private:
    string name;
    map<int, int> rep;
};
Правило нуля: Если все члены класса имеют все специальные функции, дальнейшая работа не нужна.

C.21: Если вы определяете или =delete любую операцию копирования, перемещения или деструктор, определите или =delete их все

Причина: Семантика копирования, перемещения и уничтожения тесно связана.

Правило пяти: Если вы определяете одну из этих операций, определите или =delete все пять.

C.30: Определите деструктор, если классу нужно явное действие при уничтожении объекта

Причина: Деструктор неявно вызывается в конце времени жизни объекта. Если деструктор по умолчанию достаточен, используйте его.

template<typename A>
struct final_action {   // упрощённая версия
    A act;
    final_action(A a) : act{a} {}
    ~final_action() { act(); }
};

template<typename A>
final_action<A> finally(A act)
{
    return final_action<A>{act};
}

void test()
{
    auto act = finally([] { cout << "Выход из test\n"; });
    // ...
    if (something) return;   // act выполнен здесь
    // ...
} // act выполнен здесь

C.42: Если конструктор не может создать валидный объект, выбросьте исключение

Причина: Оставить невалидный объект — это просить неприятностей.

class X2 {
    FILE* f;
    // ...
public:
    X2(const string& name)
        :f{fopen(name.c_str(), "r")}
    {
        if (!f) throw runtime_error{"не удалось открыть " + name};
        // ...
    }
    // ...
};

R: Управление ресурсами

Основные правила

R.1: Управляйте ресурсами автоматически, используя дескрипторы ресурсов и RAII

Причина: Чтобы избежать утечек и сложности ручного управления ресурсами.

RAII (Resource Acquisition Is Initialization): Идиома, при которой ресурс приобретается в конструкторе и освобождается в деструкторе. 
// Плохо: возможны утечки
void send(X* x, string_view destination)
{
    auto port = open_port(destination);
    my_mutex.lock();
    // ...
    send(port, x);
    // ...
    my_mutex.unlock();
    close_port(port);
    delete x;
}

// Хорошо: автоматическая очистка ресурсов
void send(unique_ptr<X> x, string_view destination)
{
    Port port{destination};            // port владеет PortHandle
    lock_guard<mutex> guard{my_mutex}; // guard владеет блокировкой
    // ...
    send(port, x);
    // ...
} // автоматически разблокирует my_mutex и удаляет указатель в x

R.3: Сырой указатель (T*) не владеет

Причина: Нет ничего (в стандарте C++ или в большинстве кода), что говорит об обратном, и большинство сырых указателей не владеют.

void f()
{
    int* p1 = new int{7};           // плохо: сырой владеющий указатель
    auto p2 = make_unique<int>(7);  // ОК: int принадлежит unique_ptr
    // ...
}

R.5: Предпочитайте объекты с ограниченной областью видимости, не выделяйте память в куче без необходимости

Причина: Объект с ограниченной областью видимости — это локальный объект, глобальный объект или член. Это подразумевает, что нет отдельных затрат на выделение и освобождение.

// Плохо: ненужное выделение и освобождение
void f(int n)
{
    auto p = new Gadget{n};
    // ...
    delete p;
}

// Хорошо: локальная переменная
void f(int n)
{
    Gadget g{n};
    // ...
}

Умные указатели

R.20: Используйте unique_ptr или shared_ptr для представления владения

Причина: Они могут предотвратить утечки ресурсов.

void f()
{
    X* p1 { new X };              // плохо, p1 будет утекать
    auto p2 = make_unique<X>();   // хорошо, уникальное владение
    auto p3 = make_shared<X>();   // хорошо, разделяемое владение
}

R.21: Предпочитайте unique_ptr над shared_ptr, если вам не нужно разделять владение

Причина: unique_ptr концептуально проще и более предсказуем (вы знаете, когда происходит уничтожение) и быстрее (вы не поддерживаете неявно счётчик использования).

R.22: Используйте make_shared() для создания shared_ptr

Причина: make_shared даёт более краткое выражение построения. Также даёт возможность устранить отдельное выделение для счётчиков ссылок.

shared_ptr<X> p1 { new X{2} }; // плохо
auto p = make_shared<X>(2);     // хорошо

R.23: Используйте make_unique() для создания unique_ptr

Причина: make_unique даёт более краткое выражение построения. Также обеспечивает безопасность исключений в сложных выражениях.

unique_ptr<Foo> p {new Foo{7}};    // ОК: но повторяющееся
auto q = make_unique<Foo>(7);      // Лучше: нет повторения Foo

ES: Выражения и операторы

Объявления

ES.5: Держите области видимости маленькими

Причина: Читаемость. Минимизация удержания ресурсов. Избежание непреднамеренного неправильного использования значения.

void use()
{
    int i;    // плохо: i излишне доступен после цикла
    for (i = 0; i < 20; ++i) { /* ... */ }
    // нет предполагаемого использования i здесь
    
    for (int i = 0; i < 20; ++i) { /* ... */ }  // хорошо: i локальна для цикла
}

ES.20: Всегда инициализируйте объект

Причина: Избегайте ошибок "использовано до установки" и связанного с ними неопределённого поведения.

void use(int arg)
{
    int i;   // плохо: неинициализированная переменная
    // ...
    i = 7;   // инициализация i
}

// Хорошо:
void use(int arg)
{
    int i = 7;   // ОК: инициализирована
    string s;    // ОК: инициализирована по умолчанию
    // ...
}

ES.23: Предпочитайте синтаксис инициализации {}

Причина: Правила для {} инициализации проще, более общие, менее двусмысленные и безопаснее, чем для других форм инициализации.

int x {f(99)};  // хорошо
int y = x;      // хорошо
vector<int> v = {1, 2, 3, 4, 5, 6};  // хорошо

int x {7.9};   // ошибка: сужающее преобразование
int y = 7.9;   // ОК: y становится 7. Надеемся на предупреждение компилятора

ES.47: Используйте nullptr, а не 0 или NULL

Причина: Читаемость. nullptr не может быть спутан с int. nullptr также имеет хорошо определённый (очень ограничительный) тип.

void f(int);
void f(char*);
f(0);         // вызов f(int)
f(nullptr);   // вызов f(char*)

ES.48: Избегайте приведений типов

Причина: Приведения типов — хорошо известный источник ошибок и делают некоторые оптимизации ненадёжными.

Важно: Приведения типов необходимы в системном программировании, но они серьёзно переиспользуются и являются основным источником ошибок.

ES.56: Пишите std::move() только когда вам нужно явно переместить объект в другую область видимости

Причина: Мы перемещаем, а не копируем, чтобы избежать дублирования и для улучшения производительности.

// Плохо: ненужный move
vector<int> make_vector()
{
    vector<int> result;
    // ... загрузка result данными
    return std::move(result);  // плохо; просто напишите "return result;"
}

// Хорошо: язык уже знает, что переменная является кандидатом на перемещение
vector<int> make_vector()
{
    vector<int> result;
    // ... загрузка result данными
    return result;  // хорошо: RVO или перемещение
}

Операторы

ES.70: Предпочитайте switch-оператор if-оператору, когда есть выбор

Причина: Читаемость. Эффективность. switch сравнивает с константами и обычно лучше оптимизируется, чем серия проверок в if-then-else цепочке.

void use(int n)
{
    switch (n) {   // хорошо
    case 0:
        // ...
        break;
    case 7:
        // ...
        break;
    default:
        // ...
        break;
    }
}

ES.71: Предпочитайте range-for оператор for-оператору, когда есть выбор

Причина: Читаемость. Предотвращение ошибок. Эффективность.

// Плохо
for (gsl::index i = 0; i < v.size(); ++i)
    cout << v[i] << '\n';

// Хорошо
for (const auto& x : v)
    cout << x << '\n';

Per: Производительность

Основные принципы

Per.1: Не оптимизируйте без причины

Причина: Если нет необходимости в оптимизации, главный результат усилий будет больше ошибок и более высокие затраты на поддержку.

Per.2: Не оптимизируйте преждевременно

Причина: Тщательно оптимизированный код обычно больше и сложнее изменять, чем неоптимизированный код.

Per.6: Не делайте заявлений о производительности без измерений

Причина: Поле производительности завалено мифами и ложным фольклором. Современное оборудование и оптимизаторы опровергают наивные предположения.

Важно: Получение хороших измерений производительности может быть сложным и требует специализированных инструментов.

Per.11: Переместите вычисления из времени выполнения в время компиляции

Причина: Чтобы уменьшить размер кода и время выполнения.

// Старый стиль: динамическая инициализация
double square(double d) { return d*d; }
static double s2 = square(2);

// Современный стиль: вычисление на этапе компиляции
constexpr double ntimes(double d, int n)
{
    double m = 1;
    while (n--) m *= d;
    return m;
}
constexpr double s3 {ntimes(2, 3)};  // вычисление на этапе компиляции

CP: Параллелизм и параллельное выполнение

Основные правила

CP.1: Предполагайте, что ваш код будет выполняться как часть многопоточной программы

Причина: Трудно быть уверенным, что параллелизм не используется сейчас или не будет использоваться в будущем.

// Плохо: эти статические переменные вызывают гонки данных
double cached_computation(int x)
{
    static int cached_x = 0.0;
    static double cached_result = COMPUTATION_OF_ZERO;
    
    if (cached_x != x) {
        cached_x = x;
        cached_result = computation(x);
    }
    return cached_result;
}

// Хорошо: кэш хранится как данные-члены объекта
struct ComputationCache {
    int cached_x = 0;
    double cached_result = COMPUTATION_OF_ZERO;
    
    double compute(int x) {
        if (cached_x != x) {
            cached_x = x;
            cached_result = computation(x);
        }
        return cached_result;
    }
};

CP.2: Избегайте гонок данных

Причина: Если вы этого не сделаете, ничего не гарантировано работать, и тонкие ошибки будут сохраняться.

Важно: Если два потока могут обращаться к одному объекту одновременно (без синхронизации), и хотя бы один является писателем (выполняет неконстантную операцию), у вас есть гонка данных.

CP.20: Используйте RAII, никогда не используйте простые lock()/unlock()

Причина: Избегает неприятных ошибок от неосвобождённых блокировок.

mutex mtx;

// Плохо
void do_stuff()
{
    mtx.lock();
    // ... делаем что-то ...
    mtx.unlock();  // легко забыть
}

// Хорошо
void do_stuff()
{
    unique_lock<mutex> lck {mtx};
    // ... делаем что-то ...
} // автоматически разблокирует

CP.21: Используйте std::lock() или std::scoped_lock для захвата нескольких mutex

Причина: Чтобы избежать взаимоблокировок на нескольких mutex.

// Плохо: просит взаимоблокировку
// поток 1
lock_guard<mutex> lck1(m1);
lock_guard<mutex> lck2(m2);

// поток 2
lock_guard<mutex> lck2(m2);
lock_guard<mutex> lck1(m1);

// Хорошо: используйте lock()
// поток 1
lock(m1, m2);
lock_guard<mutex> lck1(m1, adopt_lock);
lock_guard<mutex> lck2(m2, adopt_lock);

// Или лучше (C++17):
scoped_lock<mutex, mutex> lck1(m1, m2);

E: Обработка ошибок

Основные правила

E.2: Выбросьте исключение, чтобы сигнализировать, что функция не может выполнить свою задачу

Причина: Чтобы сделать обработку ошибок систематической, надёжной и не повторяющейся.

struct Foo {
    vector<Thing> v;
    File_handle f;
    string s;
};

void use()
{
    Foo bar { {Thing{1}, Thing{2}, Thing{monkey}}, {"my_file", "r"}, "Here we go!"};
    // ...
}

Здесь конструкторы vector и string могут не выделить достаточную память, File_handle может не открыть файл. В каждом случае они выбрасывают исключение для обработки вызывающим use().

E.3: Используйте исключения только для обработки ошибок

Причина: Чтобы держать обработку ошибок отделённой от "обычного кода".

// Плохо: исключение не используется для обработки ошибок
int find_index(vector<string>& vec, const string& x)
{
    try {
        for (gsl::index i = 0; i < vec.size(); ++i)
            if (vec[i] == x) throw i;  // найдено x
    }
    catch (int i) {
        return i;
    }
    return -1;   // не найдено
}

// Хорошо: используйте стандартный алгоритм
auto it = find(vec.begin(), vec.end(), x);
if (it != vec.end()) return distance(vec.begin(), it);
return -1;

E.6: Используйте RAII для предотвращения утечек

Причина: Утечки обычно неприемлемы. Ручное освобождение ресурсов подвержено ошибкам.

RAII: "Resource Acquisition Is Initialization" — идиома, при которой ресурс приобретается в конструкторе и освобождается в деструкторе.

E.14: Используйте специально разработанные пользовательские типы как исключения (не встроенные типы)

Причина: Пользовательский тип может лучше передавать информацию об ошибке обработчику.

// Плохо
throw 7;
throw "something bad";
throw std::exception{};

// Хорошо
class MyException : public std::runtime_error
{
public:
    MyException(const string& msg) : std::runtime_error{msg} {}
    // ...
};

throw MyException{"something bad"};  // хорошо

E.15: Выбрасывайте по значению, ловите исключения из иерархии по ссылке

Причина: Выбрасывание по значению (не по указателю) и ловля по ссылке предотвращает копирование, особенно срезание базовых подобъектов.

// Плохо
void f()
{
    try {
        throw new widget{};  // не делайте: выбрасывайте по значению
    }
    catch (base_class e) {  // не делайте: может срезать
        // ...
    }
}

// Хорошо
void f()
{
    try {
        throw widget{};  // выбрасываем по значению
    }
    catch (const base_class& e) {  // ловим по ссылке на const
        // ...
    }
}

Con: Константы и неизменяемость

Основные правила

Con.1: По умолчанию делайте объекты неизменяемыми

Причина: Неизменяемые объекты проще для рассуждений, чем переменные.

for (const int i : c) cout << i << '\n';    // просто чтение: const

for (int i : c) cout << i << '\n';          // ПЛОХО: просто чтение

Con.2: По умолчанию делайте функции-члены const

Причина: Функция-член должна быть помечена const, если она не изменяет наблюдаемое состояние объекта.

class Point {
    int x, y;
public:
    int getx() { return x; }    // ПЛОХО, должна быть const
    
    int getx() const { return x; }  // ХОРОШО
};

Con.3: По умолчанию передавайте указатели и ссылки на const

Причина: Чтобы избежать неожиданного изменения значения вызываемой функцией.

void f(char* p);        // изменяет ли f *p? (предполагаем, что да)
void g(const char* p);  // g не изменяет *p

Con.5: Используйте constexpr для значений, которые могут быть вычислены на этапе компиляции

Причина: Лучшая производительность, лучшая проверка на этапе компиляции, гарантированное вычисление на этапе компиляции, нет возможности гонок данных.

double x = f(2);            // возможное вычисление во время выполнения
const double y = f(2);      // возможное вычисление во время выполнения
constexpr double z = f(2);  // ошибка, если f(2) не может быть вычислено на этапе компиляции

T: Шаблоны и обобщённое программирование

Основные правила

T.1: Используйте шаблоны для повышения уровня абстракции кода

Причина: Общность. Повторное использование. Эффективность.

T.2: Используйте шаблоны для выражения алгоритмов, применимых ко многим типам аргументов

Причина: Общность. Минимизация объёма исходного кода.

template<typename Iter, typename Val>
Iter find(Iter b, Iter e, Val v)
{
    // ...
}

Это основа STL. Один алгоритм find легко работает с любым видом входного диапазона.

T.10: Указывайте концепты для всех аргументов шаблона

Причина: Правильность и читаемость. Предполагаемое значение аргумента шаблона фундаментально для интерфейса шаблона.

template<input_iterator Iter, typename Val>
    requires equality_comparable_with<iter_value_t<Iter>, Val>
Iter find(Iter b, Iter e, Val v)
{
    // ...
}

T.11: Везде, где возможно, используйте стандартные концепты

Причина: "Стандартные" концепты экономят нам работу по придумыванию собственных концептов.

Примечание: Если вы не создаёте новую обобщённую библиотеку, большинство концептов, которые вам нужны, уже будут определены стандартной библиотекой.

T.40: Используйте функциональные объекты для передачи операций алгоритмам

Причина: Функциональные объекты могут нести больше информации через интерфейс, чем "простой" указатель на функцию.

bool greater(double x, double y) { return x > y; }
sort(v, greater);                                    // указатель на функцию: потенциально медленно
sort(v, [](double x, double y) { return x > y; });   // функциональный объект
sort(v, std::greater{});                             // функциональный объект

Заключение

Ключевые принципы C++ Core Guidelines:

  • Безопасность типов: Используйте систему типов для предотвращения ошибок
  • Безопасность ресурсов: Используйте RAII для автоматического управления ресурсами
  • Безопасность времени жизни: Избегайте висячих указателей и ссылок
  • Простота: Предпочитайте простые решения сложным
  • Производительность: Не жертвуйте производительностью без необходимости
  • Читаемость: Код должен быть понятным и самодокументируемым
Важно помнить: Эти рекомендации предназначены для постепенного внедрения. Не пытайтесь применить все правила сразу к большому кодовому базе. Начните с наиболее критичных правил безопасности и постепенно расширяйте их применение.

Конспект создан на основе C++ Core Guidelines (версия от 2025 года). Полный документ доступен по адресу: https://isocpp.github.io/CppCoreGuidelines/CppCoreGuidelines
