I: Интерфейсы - Подробный конспект

О разделе: Раздел I содержит рекомендации по проектированию интерфейсов. Хороший интерфейс делает код понятным, безопасным и простым в использовании. Интерфейс должен явно выражать свои требования и гарантии.

I.1: Делайте интерфейсы явными

Проблема/Контекст

Если интерфейс зависит от скрытых предположений (глобальные переменные, состояние системы, порядок вызовов), эти зависимости легко упустить при использовании интерфейса. Это приводит к ошибкам, которые сложно найти и исправить.

Решение

Все зависимости должны быть явными в интерфейсе функции. Если функция зависит от какого-то состояния, передайте его как параметр. Если функция имеет предварительные условия, документируйте их явно (используйте Expects()).

Разбор синтаксиса

  • Параметры: Все входные данные должны быть параметрами функции
  • Expects(): Используйте для документирования предварительных условий
  • Ensures(): Используйте для документирования постусловий
  • Возвращаемые значения: Все выходные данные должны быть возвращаемыми значениями

Как это работает?

Явный интерфейс делает все зависимости очевидными. Компилятор может проверить, что все необходимые параметры переданы. Статический анализатор может проверить предварительные условия. Программист видит все зависимости без чтения реализации.

❌ Как НЕ надо

// Плохо: неявная зависимость от глобальной переменной
bool round_up = false;  // глобальная переменная

int round(double d) {
    return round_up ? std::ceil(d) : std::floor(d);
}

// Использование:
round(3.7);  // результат зависит от глобального состояния!
// Что вернёт функция? Неизвестно без проверки round_up

// Плохо: неявная зависимость от порядка вызовов
class Calculator {
    double last_result;
public:
    void set_value(double x) { last_result = x; }
    double multiply(double factor) {
        return last_result *= factor;  // зависит от set_value
    }
};

// Использование:
Calculator calc;
calc.multiply(2.0);  // ОШИБКА! last_result не инициализирован

// Плохо: неявная зависимость от состояния файловой системы
std::string read_config() {
    std::ifstream file("config.txt");  // файл должен существовать
    // ...
}

Проблемы:

  • Зависимость от глобального состояния неочевидна
  • Порядок вызовов критичен, но не документирован
  • Требование существования файла не указано
  • Сложно тестировать и отлаживать

✅ Как надо

// Хорошо: явный параметр вместо глобальной переменной
enum class RoundingMode {
    Floor,
    Ceil,
    Nearest
};

int round(double d, RoundingMode mode) {
    switch (mode) {
        case RoundingMode::Floor:
            return static_cast<int>(std::floor(d));
        case RoundingMode::Ceil:
            return static_cast<int>(std::ceil(d));
        case RoundingMode::Nearest:
            return static_cast<int>(std::round(d));
    }
}

// Использование:
round(3.7, RoundingMode::Ceil);  // явно указано поведение

// Хорошо: явные параметры вместо скрытого состояния
class Calculator {
public:
    double multiply(double value, double factor) {
        return value * factor;  // не зависит от состояния
    }
};

// Использование:
Calculator calc;
double result = calc.multiply(5.0, 2.0);  // явно и понятно

// Хорошо: явное указание файла и обработка ошибок
std::string read_config(const std::filesystem::path& config_path) {
    std::ifstream file(config_path);
    if (!file.is_open()) {
        throw std::runtime_error("Не удалось открыть файл: " + 
                                 config_path.string());
    }
    // ...
}

Преимущества:

  • Все зависимости явны в сигнатуре функции
  • Нет скрытого состояния
  • Легко тестировать
  • Компилятор проверяет правильность использования

Дополнительные примеры

// Пример 1: Использование Expects() для предварительных условий
#include <cassert>

// Макрос для предварительных условий (упрощённая версия)
#define Expects(condition) assert(condition)

double divide(double a, double b) {
    Expects(b != 0.0);  // явно документировано предварительное условие
    return a / b;
}

// Пример 2: Явные параметры вместо магических констант
class Database {
public:
    // Плохо: таймаут захардкожен
    // Connection connect() { ... }
    
    // Хорошо: таймаут явно указан
    Connection connect(int timeout_seconds) {
        // ...
    }
};

// Пример 3: Явное указание всех зависимостей
class Logger {
    std::ostream& output_stream;  // явная зависимость
public:
    explicit Logger(std::ostream& os) : output_stream(os) {}
    
    void log(const std::string& message) {
        output_stream << message << "\n";
    }
};

// Использование:
std::ofstream file("log.txt");
Logger logger(file);  // явно указан поток вывода
Ключевой момент: Если вы не можете понять, что делает функция, глядя только на её сигнатуру, интерфейс недостаточно явный. Все зависимости должны быть видны в объявлении функции.

I.2: Избегайте неконстантных глобальных переменных

Проблема/Контекст

Неконстантные глобальные переменные создают скрытые зависимости между различными частями программы. Любая функция может изменить глобальное состояние, что делает поведение программы непредсказуемым и сложным для понимания.

Решение

Избегайте неконстантных глобальных переменных. Используйте константы для глобальных значений. Используйте параметры функций для передачи состояния. Используйте классы для инкапсуляции состояния.

Как это работает?

Константные глобальные переменные безопасны, потому что их нельзя изменить. Параметры функций делают зависимости явными. Классы инкапсулируют состояние и контролируют доступ к нему.

❌ Как НЕ надо

// Плохо: неконстантная глобальная переменная
int global_counter = 0;

void increment() {
    ++global_counter;  // кто ещё изменяет global_counter?
}

void reset() {
    global_counter = 0;  // скрытая зависимость
}

// Проблема: невозможно понять, кто и когда изменяет global_counter
int get_value() {
    return global_counter;  // значение зависит от всей программы
}

// Плохо: глобальное состояние для конфигурации
std::string database_url;  // кто устанавливает это значение?
int max_connections;

void connect_to_database() {
    // использует database_url и max_connections
    // но откуда они берутся? Неясно!
}

Проблемы:

  • Скрытые зависимости между функциями
  • Непредсказуемое поведение
  • Сложно тестировать
  • Проблемы с многопоточностью

✅ Как надо

// Хорошо: константная глобальная переменная
constexpr int MAX_RETRIES = 3;  // безопасно, нельзя изменить

// Хорошо: класс инкапсулирует состояние
class Counter {
    int value = 0;  // приватное состояние
public:
    void increment() { ++value; }
    void reset() { value = 0; }
    int get_value() const { return value; }
};

// Использование:
Counter counter;  // локальное или член класса
counter.increment();  // явное управление состоянием

// Хорошо: конфигурация передаётся явно
struct DatabaseConfig {
    std::string url;
    int max_connections;
};

void connect_to_database(const DatabaseConfig& config) {
    // явно использует переданную конфигурацию
    // нет скрытых зависимостей
}

// Использование:
DatabaseConfig config{"localhost:5432", 10};
connect_to_database(config);  // явно передана конфигурация

Преимущества:

  • Нет скрытых зависимостей
  • Предсказуемое поведение
  • Легко тестировать
  • Безопасно для многопоточности (при правильном использовании)

Дополнительные примеры

class Logger {
    static Logger* instance;
    Logger() = default;
public:
    static Logger& get_instance() {
        if (!instance) {
            instance = new Logger();

    constexpr double PI = 3.14159265358979323846;

Важно: Инициализация глобальных объектов не полностью упорядочена. Если вы используете глобальный объект, инициализируйте его константой или используйте функцию инициализации, которая вызывается явно.

I.4: Делайте интерфейсы точно и строго типизированными

Проблема/Контекст

Использование примитивных типов (int, double, char*) для представления семантически различных понятий приводит к ошибкам. Компилятор не может различить, что два int представляют разные сущности (например, координату X и координату Y).

Решение

Создавайте пользовательские типы для различных семантических понятий. Используйте enum class вместо магических чисел. Используйте структуры для группировки связанных данных.

Как это работает?

Сильная типизация предотвращает ошибки на этапе компиляции. Если вы создали тип Point для координат, компилятор не позволит передать int вместо Point. Это делает интерфейс самодокументируемым и безопасным.

❌ Как НЕ надо

// Плохо: что означают эти числа?
void draw_rect(int x1, int y1, int x2, int y2);

// Использование:
draw_rect(100, 200, 300, 400);  // что есть что? Неясно!

// Плохо: легко перепутать порядок параметров
void set_user_info(int id, int age, int salary);
set_user_info(25, 30, 50000);  // правильно?
set_user_info(30, 25, 50000);  // ошибка, но компилятор не заметит

// Плохо: магические числа
enum Status {
    PENDING = 0,
    PROCESSING = 1,
    COMPLETED = 2,
    FAILED = 3
};

void update_status(int status);  // можно передать любое int!
update_status(42);  // ошибка, но компилятор не знает

Проблемы:

  • Неясно, что означают параметры
  • Легко перепутать порядок
  • Магические числа небезопасны
  • Ошибки обнаруживаются только во время выполнения

✅ Как надо

// Хорошо: явные типы для координат
struct Point {
    int x, y;
};

struct Size {
    int width, height;
};

void draw_rectangle(Point top_left, Point bottom_right);
void draw_rectangle(Point position, Size size);

// Использование:
Point top_left{100, 200};
Point bottom_right{300, 400};
draw_rectangle(top_left, bottom_right);  // понятно!

Size rect_size{200, 200};
draw_rectangle(top_left, rect_size);  // тоже понятно

// Хорошо: строгие типы для параметров
class UserId {
    int value;
public:
    explicit UserId(int v) : value(v) {}
    int get() const { return value; }
};

class Age {
    int value;
public:
    explicit Age(int v) : value(v) {}
    int get() const { return value; }
};

void set_user_info(UserId id, Age age, int salary);
set_user_info(UserId{25}, Age{30}, 50000);  // невозможно перепутать

// Хорошо: enum class вместо магических чисел
enum class OrderStatus {
    Pending,
    Processing,
    Completed,
    Failed
};

void update_status(OrderStatus status);
update_status(OrderStatus::Completed);  // типобезопасно
// update_status(42);  // ошибка компиляции!

Преимущества:

  • Параметры самодокументируемы
  • Невозможно перепутать порядок
  • Типобезопасность на этапе компиляции
  • Ошибки обнаруживаются компилятором

Дополнительные примеры

// Пример 1: Сильные типы для единиц измерения
class Meter {
    double value;
public:
    explicit Meter(double v) : value(v) {}
    double get() const { return value; }
};

class Kilometer {
    double value;
public:
    explicit Kilometer(double v) : value(v) {}
    double get() const { return value; }
    operator Meter() const { return Meter(value * 1000.0); }
};

double calculate_speed(Meter distance, double time) {
    return distance.get() / time;
}

// Использование:
Meter m{1000};
Kilometer km{1};
calculate_speed(m, 60.0);      // ОК
calculate_speed(km, 60.0);     // ОК, неявное преобразование
// calculate_speed(1000, 60.0); // ошибка компиляции!

// Пример 2: Типы для идентификаторов
template<typename Tag>
class Id {
    int value;
public:
    explicit Id(int v) : value(v) {}
    int get() const { return value; }
    bool operator==(const Id<Tag>& other) const {
        return value == other.value;
    }
};

struct UserTag {};
struct OrderTag {};

using UserId = Id<UserTag>;
using OrderId = Id<OrderTag>;

void process_order(UserId user_id, OrderId order_id) {
    // ...
}

// Использование:
UserId uid{123};
OrderId oid{456};
process_order(uid, oid);  // ОК
// process_order(oid, uid);  // ошибка компиляции!
Правило: Если два значения имеют разную семантику, они должны иметь разные типы. Это предотвращает ошибки и делает код более понятным.

I.10: Используйте исключения для сигнализации о невозможности выполнить требуемую задачу

Проблема/Контекст

Когда функция не может выполнить свою задачу, она должна каким-то образом сообщить об этом. Использование специальных значений (например, -1, nullptr, false) для обозначения ошибок приводит к тому, что эти значения можно игнорировать, что приводит к неопределённому поведению.

Решение

Используйте исключения для сигнализации об ошибках. Исключения нельзя игнорировать - они должны быть обработаны, иначе программа завершится. Это гарантирует, что ошибки не останутся незамеченными.

Как это работает?

Когда функция выбрасывает исключение, выполнение функции прерывается, и исключение распространяется вверх по стеку вызовов до тех пор, пока не будет поймано обработчиком catch. Если исключение не поймано, программа завершается.

❌ Как НЕ надо

// Плохо: возврат специального значения при ошибке
int divide(int a, int b) {
    if (b == 0) {
        return -1;  // что означает -1? Ошибка? Результат?
    }
    return a / b;
}

// Использование:
int result = divide(10, 0);
// result = -1, но что это значит? Можно забыть проверить
result = result * 2;  // используем -1 как обычное значение!

// Плохо: возврат nullptr при ошибке
int* find_element(const std::vector<int>& vec, int value) {
    for (auto& x : vec) {
        if (x == value) {
            return &x;
        }
    }
    return nullptr;  // можно забыть проверить
}

// Использование:
int* ptr = find_element(vec, 42);
*ptr = 100;  // ОШИБКА! если ptr == nullptr

// Плохо: возврат bool для обозначения успеха
bool read_file(const std::string& filename, std::string& content) {
    std::ifstream file(filename);
    if (!file.is_open()) {
        return false;  // можно забыть проверить
    }
    // ...
    return true;
}

// Использование:
std::string data;
read_file("nonexistent.txt", data);  // забыли проверить результат!
process(data);  // data может быть пустой

Проблемы:

  • Специальные значения можно игнорировать
  • Легко забыть проверить результат
  • Неясно, что означает специальное значение
  • Ошибки могут остаться незамеченными

✅ Как надо

// Хорошо: исключение при ошибке
#include <stdexcept>

int divide(int a, int b) {
    if (b == 0) {
        throw std::invalid_argument("Деление на ноль");
    }
    return a / b;
}

// Использование:
try {
    int result = divide(10, 0);
    // этот код не выполнится, если b == 0
} catch (const std::invalid_argument& e) {
    // ошибка обработана явно
    std::cerr << "Ошибка: " << e.what() << "\n";
}

// Хорошо: исключение вместо nullptr
#include <algorithm>

int& find_element(std::vector<int>& vec, int value) {
    auto it = std::find(vec.begin(), vec.end(), value);
    if (it == vec.end()) {
        throw std::runtime_error("Элемент не найден");
    }
    return *it;
}

// Использование:
try {
    int& element = find_element(vec, 42);
    element = 100;  // безопасно, элемент гарантированно существует
} catch (const std::runtime_error& e) {
    // обработали ошибку
}

// Хорошо: исключение вместо bool
std::string read_file(const std::string& filename) {
    std::ifstream file(filename);
    if (!file.is_open()) {
        throw std::runtime_error("Не удалось открыть файл: " + filename);
    }
    
    std::string content;
    std::string line;
    while (std::getline(file, line)) {
        content += line + "\n";
    }
    
    return content;  // возвращаем значение, а не статус
}

// Использование:
try {
    std::string data = read_file("data.txt");
    process(data);  // data гарантированно содержит данные
} catch (const std::runtime_error& e) {
    // обработали ошибку открытия файла
}

Преимущества:

  • Исключения нельзя игнорировать
  • Ошибки обрабатываются явно
  • Нормальный путь выполнения не засоряется проверками
  • Тип ошибки передаётся через тип исключения

Дополнительные примеры

// Пример 1: Специализированные типы исключений
class FileNotFoundError : public std::runtime_error {
public:
    explicit FileNotFoundError(const std::string& filename)
        : std::runtime_error("Файл не найден: " + filename) {}
};

class PermissionDeniedError : public std::runtime_error {
public:
    explicit PermissionDeniedError(const std::string& filename)
        : std::runtime_error("Доступ запрещён: " + filename) {}
};

std::string read_file_safe(const std::string& filename) {
    std::ifstream file(filename);
    if (!file.is_open()) {
        if (!std::filesystem::exists(filename)) {
            throw FileNotFoundError(filename);
        } else {
            throw PermissionDeniedError(filename);
        }
    }
    // ...
}

// Пример 2: Использование std::optional для опциональных значений
#include <optional>

std::optional<int> safe_divide(int a, int b) {
    if (b == 0) {
        return std::nullopt;  // не ошибка, а отсутствие значения
    }
    return a / b;
}

// Использование:
auto result = safe_divide(10, 2);
if (result.has_value()) {
    std::cout << "Результат: " << result.value() << "\n";
} else {
    std::cout << "Деление невозможно\n";
}
Важно: Используйте исключения для ошибок, которые нарушают контракт функции. Для опциональных значений (когда отсутствие значения - это нормальная ситуация) используйте std::optional.

I.11: Никогда не передавайте владение через сырой указатель (T*) или ссылку (T&)

Проблема/Контекст

Когда функция возвращает сырой указатель или принимает ссылку, неясно, кто владеет объектом и кто отвечает за его удаление. Это приводит к утечкам памяти или двойному удалению.

Решение

Используйте умные указатели (unique_ptr, shared_ptr) для передачи владения. Используйте ссылки для объектов, которые не принадлежат функции. Используйте возврат по значению для небольших объектов.

Как это работает?

Умные указатели автоматически управляют временем жизни объекта. unique_ptr передаёт единоличное владение, shared_ptr позволяет разделять владение. Возврат по значению использует move semantics для эффективной передачи больших объектов.

❌ Как НЕ надо

// Плохо: неясно, кто владеет возвращённым объектом
X* create_x() {
    X* x = new X{};
    // ...
    return x;  // кто должен удалить x?
}

// Использование:
X* ptr = create_x();
// ... использование ptr ...
// Кто удаляет ptr? Неясно!
// delete ptr;  // может быть ошибкой, если владелец другой

// Плохо: передача владения через ссылку
void take_ownership(X& x) {
    // функция владеет x? Или просто использует?
    // ...
    delete &x;  // опасно! x может быть не в куче
}

// Плохо: неясно, кто владеет параметром
void process(X* x) {
    // x принадлежит функции? Или просто используется?
    // нужно ли удалять x?
}

Проблемы:

  • Неясно, кто владеет объектом
  • Легко забыть удалить объект
  • Возможны утечки памяти
  • Возможно двойное удаление

✅ Как надо

// Хорошо: unique_ptr явно передаёт владение
#include <memory>

std::unique_ptr<X> create_x() {
    auto x = std::make_unique<X>();
    // ...
    return x;  // владение передаётся вызывающему
}

// Использование:
auto ptr = create_x();
// ptr автоматически удалит X при выходе из области видимости

// Хорошо: передача владения через unique_ptr
void take_ownership(std::unique_ptr<X> x) {
    // функция явно принимает владение
    // x автоматически удалится при выходе из функции
}

// Использование:
auto x = std::make_unique<X>();
take_ownership(std::move(x));  // явная передача владения
// x теперь nullptr

// Хорошо: возврат по значению (move semantics)
#include <vector>

std::vector<double> compute_data() {
    std::vector<double> result(10000);
    // ... заполнение result ...
    return result;  // эффективно перемещается, не копируется
}

// Использование:
auto data = compute_data();  // эффективно, без копирования

// Хорошо: ссылка для объектов без владения
void process(const X& x) {
    // функция не владеет x, просто использует
    // x должен существовать вне функции
}

// Использование:
X x;
process(x);  // x существует независимо от process

Преимущества:

  • Владение явно выражено в типе
  • Автоматическое управление памятью
  • Нет утечек памяти
  • Нет двойного удаления

Дополнительные примеры

// Пример 1: Разделяемое владение через shared_ptr
#include <memory>

class Resource {
    // ...
};

std::shared_ptr<Resource> create_shared_resource() {
    return std::make_shared<Resource>();
}

void use_resource(std::shared_ptr<Resource> res) {
    // res разделяет владение с вызывающим
    // Resource удалится, когда последний shared_ptr уничтожится
}

// Использование:
auto resource = create_shared_resource();
use_resource(resource);  // оба владеют Resource
// Resource удалится, когда оба shared_ptr уничтожатся

// Пример 2: Возврат по значению для небольших объектов
struct Point {
    double x, y;
};

Point create_point(double x, double y) {
    return Point{x, y};  // эффективно даже без move
}

// Пример 3: Использование observer_ptr для невладеющих указателей
template<typename T>
using observer_ptr = T*;  // указатель без владения

void observe(observer_ptr<const X> x) {
    // функция наблюдает за x, но не владеет им
    // x должен существовать вне функции
}
Правило: Если функция создаёт объект и возвращает его, используйте unique_ptr или возврат по значению. Если функция только использует объект, передавайте по ссылке или observer_ptr. Никогда не используйте сырой указатель для передачи владения.

Заключение

Ключевые принципы раздела I (Интерфейсы):

  • Явность: Все зависимости должны быть явными в интерфейсе
  • Избегание глобальных переменных: Используйте параметры и инкапсуляцию
  • Строгая типизация: Используйте типы для выражения семантики
  • Исключения для ошибок: Используйте исключения вместо специальных значений
  • Явное владение: Используйте умные указатели для передачи владения
Важно: Хороший интерфейс делает код понятным и безопасным. Плохой интерфейс создаёт скрытые зависимости и приводит к ошибкам. Всегда думайте о том, как будет использоваться ваш интерфейс.
