P: Философия - Подробный конспект

О разделе: Раздел P содержит фундаментальные принципы программирования на C++. Эти правила формируют основу для всех остальных рекомендаций и помогают понять философию современного C++.

P.1: Выражайте идеи напрямую в коде

Проблема/Контекст

Компиляторы не читают комментарии. Если важная информация о коде находится только в комментариях, она может быть упущена, неправильно понята или устареть. Код, который выражает свои намерения напрямую через типы, имена и структуру, более надёжен и понятен.

Решение

Используйте систему типов C++ для выражения семантики. Выбирайте осмысленные имена. Структурируйте код так, чтобы его назначение было очевидным без комментариев.

Разбор синтаксиса

  • Типы: Используйте пользовательские типы вместо примитивов для выражения семантики
  • Имена: Выбирайте имена, которые отражают назначение переменной или функции
  • const: Используйте const для выражения неизменяемости
  • Структура: Организуйте код так, чтобы его логика была очевидной

Как это работает?

Компилятор проверяет типы на этапе компиляции. Если вы используете тип Month вместо int, компилятор не позволит передать невалидное значение. Это предотвращает ошибки, которые комментарии не могут предотвратить.

❌ Как НЕ надо

// Плохо: неясно, что возвращается
// Возвращает номер месяца (1-12)
int month();

// Плохо: неясно, что означают параметры
void process(int a, int b, int c);

// Плохо: магические числа без объяснения
if (status == 3) {
    // что означает 3?
}

// Плохо: комментарий объясняет, что делает код
// Увеличиваем счётчик на 1
counter = counter + 1;

Проблемы:

  • Тип int не передаёт семантику месяца
  • Параметры a, b, c не имеют смысла
  • Магическое число 3 требует комментария
  • Комментарий дублирует код

✅ Как надо

// Хорошо: тип выражает семантику
enum class Month {
    January = 1, February, March, April, May, June,
    July, August, September, October, November, December
};
Month current_month() const;  // явно возвращает месяц

// Хорошо: осмысленные имена параметров
void process(UserId user_id, OrderId order_id, PaymentId payment_id);

// Хорошо: именованная константа вместо магического числа
enum class OrderStatus { Pending, Processing, Completed, Cancelled };
if (status == OrderStatus::Completed) {
    // намерение очевидно из кода
}

// Хорошо: код самодокументируемый
increment_counter();  // имя функции выражает действие

Преимущества:

  • Тип Month предотвращает ошибки
  • Имена параметров объясняют назначение
  • Константа OrderStatus::Completed понятна
  • Код не требует комментариев

Дополнительные примеры

// Пример 1: Использование типов для безопасности
class Temperature {
    double value;
public:
    explicit Temperature(double v) : value(v) {
        if (v < -273.15) throw std::invalid_argument("Ниже абсолютного нуля");
    }
    double get_celsius() const { return value; }
    double get_fahrenheit() const { return value * 9.0/5.0 + 32.0; }
};

// Использование:
Temperature temp{25.0};  // тип выражает, что это температура
// temp = 25.0;  // ошибка компиляции - нельзя присвоить double

// Пример 2: Использование enum class вместо магических чисел
enum class FileMode {
    ReadOnly,
    WriteOnly,
    ReadWrite
};

void open_file(const std::string& path, FileMode mode) {
    // mode может быть только одним из трёх значений
    // компилятор предотвратит передачу невалидного значения
}

// Использование:
open_file("data.txt", FileMode::ReadOnly);  // понятно и безопасно
Ключевой момент: Код, который выражает идеи напрямую, легче читать, понимать и поддерживать. Компилятор может проверить типы, но не может проверить комментарии.

P.2: Пишите на стандартном ISO C++

Проблема/Контекст

Многие компиляторы поддерживают расширения языка, которые не являются частью стандарта C++. Использование таких расширений делает код непереносимым и может привести к проблемам при переходе на другой компилятор или платформу.

Решение

Используйте только стандартные возможности ISO C++. Настройте компилятор так, чтобы он отклонял нестандартные расширения.

Разбор синтаксиса

  • Стандарт C++: Используйте возможности из стандарта (C++17, C++20, C++23)
  • Флаги компилятора: Используйте флаги типа -pedantic, -std=c++20 для строгой проверки
  • Избегайте: Расширений компилятора (например, __attribute__, #pragma)

❌ Как НЕ надо

// Плохо: использование расширения GCC
void func() __attribute__((deprecated));

// Плохо: использование нестандартного типа
__int128 big_number;  // не стандарт C++

// Плохо: использование нестандартных макросов
#ifdef _MSC_VER
    // код только для MSVC
#endif

// Плохо: использование нестандартных библиотек
#include <windows.h>  // специфично для Windows

✅ Как надо

// Хорошо: стандартный C++ атрибут
[[deprecated("Используйте new_func()")]]
void func();

// Хорошо: стандартный тип из <cstdint>
#include <cstdint>
std::int64_t big_number;  // стандартный тип

// Хорошо: стандартные возможности
#include <filesystem>  // стандартная библиотека C++17
namespace fs = std::filesystem;

// Хорошо: кроссплатформенный код
#include <fstream>  // стандартная библиотека
Важно: Если вам действительно нужно использовать расширения компилятора (например, для оптимизации), изолируйте их в отдельные модули и документируйте зависимость от конкретного компилятора.

P.3: Выражайте намерения

Проблема/Контекст

Код может быть технически правильным, но если его намерение неясно, его сложно понять, поддерживать и изменять. Неясные намерения приводят к ошибкам при модификации кода.

Решение

Используйте конструкции языка, которые явно выражают ваше намерение. Предпочитайте range-based for обычным циклам, алгоритмы STL ручным циклам, умные указатели сырым указателям.

Как это работает?

Когда вы используете range-based for, намерение "пройти по всем элементам" очевидно. Когда вы используете std::find, намерение "найти элемент" очевидно. Компилятор и другие программисты понимают ваши намерения без дополнительных объяснений.

❌ Как НЕ надо

// Плохо: неясно намерение
gsl::index i = 0;
while (i < v.size()) {
    process(v[i]);
    ++i;
}

// Плохо: неясно, что мы ищем
bool found = false;
for (gsl::index i = 0; i < vec.size(); ++i) {
    if (vec[i] == target) {
        found = true;
        break;
    }
}

// Плохо: неясно, что делает этот код
int* p = get_pointer();
if (p != nullptr) {
    use(*p);
    delete p;
}

Проблемы:

  • Неясно, что мы просто проходим по элементам
  • Ручной поиск скрывает намерение
  • Неясно, кто владеет указателем

✅ Как надо

// Хорошо: намерение очевидно - пройти по всем элементам
for (const auto& x : v) {
    process(x);
}

// Хорошо: намерение найти элемент выражено явно
auto it = std::find(vec.begin(), vec.end(), target);
bool found = (it != vec.end());

// Хорошо: намерение владения выражено через unique_ptr
std::unique_ptr<int> p = get_pointer();
if (p) {
    use(*p);
    // автоматическое освобождение памяти
}

Преимущества:

  • Намерение "пройти по элементам" очевидно
  • std::find явно выражает поиск
  • unique_ptr выражает владение

Дополнительные примеры

// Пример 1: Использование алгоритмов STL
#include <algorithm>
#include <vector>
#include <numeric>

std::vector<int> numbers = {1, 2, 3, 4, 5};

// Плохо: ручной подсчёт суммы
int sum = 0;
for (size_t i = 0; i < numbers.size(); ++i) {
    sum += numbers[i];
}

// Хорошо: намерение "суммировать" выражено явно
int sum = std::accumulate(numbers.begin(), numbers.end(), 0);

// Пример 2: Использование range-based for для контейнеров
std::map<std::string, int> scores = {{"Alice", 100}, {"Bob", 85}};

// Плохо: ручной обход
for (auto it = scores.begin(); it != scores.end(); ++it) {
    std::cout << it->first << ": " << it->second << "\n";
}

// Хорошо: намерение "пройти по парам" очевидно
for (const auto& [name, score] : scores) {
    std::cout << name << ": " << score << "\n";
}

P.4: В идеале программа должна быть статически типобезопасной

Проблема/Контекст

Ошибки типов, обнаруженные во время выполнения, могут привести к сбоям программы. Статическая типобезопасность позволяет обнаруживать ошибки на этапе компиляции, когда их исправить проще и дешевле.

Решение

Используйте систему типов C++ для предотвращения ошибок. Избегайте небезопасных конструкций: union без тегов, небезопасных приведений типов, распада массивов.

Проблемные области

  • Union: Может содержать разные типы, но компилятор не знает, какой активен
  • Приведения типов: Обходят систему типов
  • Распад массивов: Массив превращается в указатель, теряется информация о размере
  • Ошибки диапазона: Доступ за пределами массива
  • Сужение преобразований: Потеря данных при преобразовании типов

❌ Как НЕ надо

// Плохо: union без тега - небезопасно
union Value {
    int i;
    double d;
    char* s;
};
Value v;
v.i = 42;
// Какой тип активен? Неизвестно!

// Плохо: небезопасное приведение типа
void* ptr = malloc(100);
int* int_ptr = (int*)ptr;  // небезопасно

// Плохо: распад массива
void process(int arr[]) {  // на самом деле int*
    // размер массива потерян!
}

// Плохо: доступ за пределами массива
int arr[10];
arr[15] = 42;  // неопределённое поведение

✅ Как надо

// Хорошо: std::variant вместо union
#include <variant>
std::variant<int, double, std::string> v = 42;
// Тип известен и проверяется компилятором

// Хорошо: std::any или шаблоны вместо void*
template<typename T>
std::unique_ptr<T> allocate() {
    return std::make_unique<T>();
}

// Хорошо: std::array или std::span вместо распада
#include <array>
#include <span>
void process(std::span<int> arr) {
    // размер доступен через arr.size()
}

// Хорошо: проверка границ
#include <vector>
std::vector<int> vec(10);
if (index < vec.size()) {
    vec[index] = 42;  // безопасно
}

Дополнительные примеры

// Пример: Использование std::variant для типобезопасного union
#include <variant>
#include <string>
#include <iostream>

using Value = std::variant<int, double, std::string>;

void print_value(const Value& v) {
    // Компилятор заставляет обработать все возможные типы
    std::visit([](auto&& val) {
        std::cout << val << "\n";
    }, v);
}

// Использование:
Value v1 = 42;
Value v2 = 3.14;
Value v3 = std::string("Hello");

print_value(v1);  // безопасно и типобезопасно

// Пример: Использование std::span для безопасной работы с массивами
#include <span>
#include <array>

void process_data(std::span<const int> data) {
    // data.size() всегда доступен
    for (size_t i = 0; i < data.size(); ++i) {
        // безопасный доступ
        std::cout << data[i] << " ";
    }
}

std::array<int, 5> arr = {1, 2, 3, 4, 5};
process_data(arr);  // безопасно передать массив
Важно: Статическая типобезопасность не гарантирует отсутствие всех ошибок, но она предотвращает множество распространённых ошибок на этапе компиляции, когда их исправить проще всего.

P.5: Предпочитайте проверки на этапе компиляции проверкам во время выполнения

Проблема/Контекст

Проверки во время выполнения требуют дополнительного кода, могут быть пропущены и обнаруживают ошибки только при выполнении программы. Проверки на этапе компиляции не требуют дополнительного кода во время выполнения и обнаруживают ошибки до запуска программы.

Решение

Используйте static_assert для проверок на этапе компиляции. Используйте constexpr для вычислений на этапе компиляции. Используйте систему типов для предотвращения ошибок.

Как это работает?

static_assert проверяет условие на этапе компиляции. Если условие ложно, компиляция завершается с ошибкой. constexpr позволяет вычислять значения на этапе компиляции, что даёт возможность использовать их в static_assert и других контекстах, требующих констант времени компиляции.

❌ Как НЕ надо

// Плохо: проверка во время выполнения
int bits = 0;
for (int i = 1; i; i <<= 1)
    ++bits;
if (bits < 32)
    std::cerr << "Int слишком мал\n";

// Плохо: проверка во время выполнения
template<typename T>
void process(T value) {
    if (sizeof(T) < 4) {
        throw std::runtime_error("Тип слишком мал");
    }
    // ...
}

// Плохо: вычисление во время выполнения
double calculate_pi() {
    return 3.14159265358979323846;
}
const double pi = calculate_pi();  // вычисляется во время выполнения

Проблемы:

  • Ошибка обнаруживается только при выполнении
  • Требуется дополнительный код проверки
  • Может быть пропущена при тестировании

✅ Как надо

// Хорошо: проверка на этапе компиляции
static_assert(sizeof(int) >= 4, "Int должен быть минимум 32 бита");

// Хорошо: проверка на этапе компиляции в шаблоне
template<typename T>
void process(T value) {
    static_assert(sizeof(T) >= 4, "Тип должен быть минимум 32 бита");
    // ...
}

// Хорошо: вычисление на этапе компиляции
constexpr double calculate_pi() {
    return 3.14159265358979323846;
}
constexpr double pi = calculate_pi();  // вычисляется на этапе компиляции

Преимущества:

  • Ошибка обнаруживается на этапе компиляции
  • Нет накладных расходов во время выполнения
  • Невозможно пропустить при тестировании

Дополнительные примеры

// Пример 1: Проверка размера типа на этапе компиляции
#include <cstdint>

// Проверяем, что int64_t действительно 64 бита
static_assert(sizeof(std::int64_t) == 8, 
              "int64_t должен быть 8 байт");

// Пример 2: Проверка свойств типа
template<typename T>
class Container {
    static_assert(std::is_copy_constructible_v<T>,
                  "T должен быть копируемым");
    static_assert(std::is_destructible_v<T>,
                  "T должен быть уничтожаемым");
    // ...
};

// Пример 3: Вычисление на этапе компиляции
constexpr int factorial(int n) {
    return (n <= 1) ? 1 : n * factorial(n - 1);
}

constexpr int fact_5 = factorial(5);  // вычисляется на этапе компиляции
static_assert(fact_5 == 120, "5! должно быть 120");

// Пример 4: Проверка условий компиляции
template<typename T>
void safe_divide(T a, T b) {
    static_assert(std::is_arithmetic_v<T>,
                  "T должен быть арифметическим типом");
    // ...
}
Правило: Если что-то можно проверить на этапе компиляции, проверьте это на этапе компиляции. Это быстрее, надёжнее и не требует дополнительного кода во время выполнения.

P.8: Не допускайте утечек ресурсов

Проблема/Контекст

Ресурсы (память, файлы, сетевые соединения, блокировки) ограничены. Если ресурсы не освобождаются после использования, они накапливаются и в конечном итоге исчерпываются, что приводит к сбою программы.

Решение

Используйте RAII (Resource Acquisition Is Initialization) - идиому, при которой ресурс приобретается в конструкторе и освобождается в деструкторе. Используйте умные указатели для управления памятью, контейнеры STL для управления данными.

Как это работает?

RAII гарантирует, что ресурс будет освобождён при выходе из области видимости, даже если произойдёт исключение. Деструктор вызывается автоматически при выходе из области видимости или при выбрасывании исключения.

❌ Как НЕ надо

// Плохо: возможна утечка файлового дескриптора
void process_file(const char* name) {
    FILE* input = fopen(name, "r");
    if (!input) return;  // утечка, если файл не открыт
    
    char buffer[100];
    if (fgets(buffer, sizeof(buffer), input) == nullptr) {
        fclose(input);  // нужно не забыть закрыть
        return;
    }
    
    // обработка данных...
    
    if (error_condition) {
        return;  // УТЕЧКА! файл не закрыт
    }
    
    fclose(input);  // легко забыть
}

// Плохо: утечка памяти
void allocate_memory() {
    int* ptr = new int[1000];
    // ... использование ...
    if (some_condition) {
        return;  // УТЕЧКА! память не освобождена
    }
    delete[] ptr;  // легко забыть
}

// Плохо: утечка блокировки
std::mutex mtx;
void critical_section() {
    mtx.lock();
    // ... работа ...
    if (error) {
        return;  // УТЕЧКА! блокировка не снята
    }
    mtx.unlock();  // легко забыть
}

Проблемы:

  • Легко забыть освободить ресурс
  • При исключении ресурс не освобождается
  • Код становится сложным из-за множества точек выхода

✅ Как надо

// Хорошо: RAII автоматически закрывает файл
#include <fstream>
#include <string>

void process_file(const std::string& name) {
    std::ifstream input(name);  // автоматически откроется
    if (!input.is_open()) {
        return;  // автоматически закроется при выходе
    }
    
    std::string line;
    if (!std::getline(input, line)) {
        return;  // автоматически закроется
    }
    
    // обработка данных...
    
    if (error_condition) {
        return;  // автоматически закроется
    }
    // файл автоматически закроется при выходе из функции
}

// Хорошо: умный указатель автоматически освобождает память
#include <memory>
#include <vector>

void allocate_memory() {
    auto ptr = std::make_unique<int[]>(1000);
    // ... использование ...
    if (some_condition) {
        return;  // память автоматически освободится
    }
    // память автоматически освободится при выходе
}

// Хорошо: lock_guard автоматически снимает блокировку
#include <mutex>
std::mutex mtx;

void critical_section() {
    std::lock_guard<std::mutex> lock(mtx);
    // ... работа ...
    if (error) {
        return;  // блокировка автоматически снимется
    }
    // блокировка автоматически снимется при выходе
}

Преимущества:

  • Ресурс автоматически освобождается
  • Работает даже при исключениях
  • Код проще и понятнее

// Пример 1: Собственный RAII класс для ресурса
class DatabaseConnection {
    void* connection_handle;
public:
    DatabaseConnection(const std::string& connection_string) {
        connection_handle = open_connection(connection_string);
        if (!connection_handle) {
            throw std::runtime_error("Не удалось подключиться");
        }
    }
    
    ~DatabaseConnection() {
        if (connection_handle) {
            close_connection(connection_handle);
        }
    }
    
    // Удаляем копирование и присваивание
    DatabaseConnection(const DatabaseConnection&) = delete;
    DatabaseConnection& operator=(const DatabaseConnection&) = delete;
    
    // Разрешаем перемещение
    DatabaseConnection(DatabaseConnection&& other) noexcept
        : connection_handle(other.connection_handle) {
        other.connection_handle = nullptr;
    }
    
    void execute_query(const std::string& query) {
        // использование connection_handle
    }
};

// Использование:
void process_database() {
    DatabaseConnection db("server=localhost;database=mydb");
    // ... работа с базой данных ...
    // соединение автоматически закроется при выходе
}

// Пример 2: Использование finally для гарантированной очистки
#include <functional>

template<typename F>
class Finally {
    F cleanup;
public:
    explicit Finally(F f) : cleanup(std::move(f)) {}
    ~Finally() { cleanup(); }
    
    Finally(const Finally&) = delete;
    Finally& operator=(const Finally&) = delete;
};

template<typename F>
Finally<F> make_finally(F f) {
    return Finally<F>(std::move(f));
}

void example() {
    int* resource = acquire_resource();
    auto cleanup = make_finally([resource]() {
        release_resource(resource);
    });
    
    // ... работа с ресурсом ...
    // ресурс автоматически освободится при выходе
}
Правило нуля: Если вы используете RAII правильно, вам не нужно вручную управлять ресурсами. Деструкторы делают это автоматически.

Заключение

Ключевые принципы раздела P (Философия):

  • Выражайте идеи в коде: Используйте типы и имена для выражения семантики
  • Стандартный C++: Избегайте расширений компилятора
  • Явные намерения: Код должен быть самодокументируемым
  • Типобезопасность: Используйте систему типов для предотвращения ошибок
  • Проверки на этапе компиляции: Предпочитайте статические проверки динамическим
  • RAII: Используйте автоматическое управление ресурсами
Важно: Эти принципы формируют основу для всех остальных рекомендаций C++ Core Guidelines. Понимание философии поможет применять остальные правила более осознанно.

Конспект создан на основе C++ Core Guidelines. Полный документ: https://isocpp.github.io/CppCoreGuidelines/CppCoreGuidelines
