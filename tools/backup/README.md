# BackupService

Самостоятельная утилита полных независимых снимков и экономной пофайловой
истории файлов и рабочих SQLite.
`SearchEngine` не запускает и не линкует этот код.

## Сборка

```text
cmake --build <build-dir> --config Release --target BackupService
```

Цель не зависит от поискового сервера, OpenSSL или utf8proc. Для безопасного
копирования открытых баз в неё статически встроена отдельная официальная
SQLite 3.53.4.

## Запуск

Постоянный режим:

```text
BackupService --config Backup.json
```

Все задания запускаются сразу, затем повторяются через свой `period_sec`.
Остановка выполняется через `Ctrl+C`.

Разовый запуск:

```text
BackupService --config Backup.json --once
```

Код возврата:

- `0` — все источники успешно сохранены либо не изменились;
- `1` — ошибка создания хотя бы одного снимка;
- `2` — ошибка аргументов или конфигурации.

Пример конфигурации находится в `Backup.example.json`.

Готовые профили для каталогов AutoPad (`BASES`, `BASES_PRD`, `F12`,
`OTPRAVKA`, `TVRD`) находятся в `configs/autopad/`. Основной файл для одного
процесса — `configs/autopad/Backup.all.json`.

Экономный профиль, в котором неизменившиеся файлы не копируются в каждую
версию, находится в
`configs/autopad-economical/Backup.economical.json`.

Стратегии цели:

- `snapshot` (по умолчанию) — существующие полные независимые снимки;
- `mirror_history` — одно актуальное зеркало, уникальные старые версии
  изменённых файлов и маленькие манифесты точек восстановления.

Для `mirror_history` требуется `history_periods`. Например:

```json
"history_periods": [
  {"every": "1min", "keep": 60},
  {"every": "1h", "keep": 48},
  {"every": "1d", "keep": 31}
]
```

Поддерживаются `s`, `min`, `h`, `d`, `w`, `mo`; месяц равен 30 суткам.
Фактический интервал не может быть меньше `period_sec` группы.
Подробности находятся в `docs/BACKUP_MIRROR_HISTORY.md`.

Режимы цели:

- `auto` (по умолчанию) — файлы SQLite копируются через Online Backup API,
  остальные файлы — стабильным файловым копированием; неизменившиеся
  проверенные файлы повторно используются через внутренний пофайловый кэш;
- `filesystem` — побайтовое копирование всех файлов без SQLite-обработки.

Дополнительные настройки цели:

- `cache` (по умолчанию `true`) — сохранять проверенные пофайловые артефакты
  между запусками. Для часто изменяющейся отдельной `ARCHIVE.db3` лучше
  `false`: Online Backup сразу пишется в снимок без второй записи в кэш;
- `skip_unchanged` (по умолчанию `false`) — не создавать новую версию, если
  источник надёжно признан неизменившимся, а последний снимок существует и
  проходит проверку.

Для частого и полного резервирования следует создать две группы с одинаковым
`backup_dir`: отдельные `ARCHIVE.db3` с `period_sec: 60`, `cache: false` и
полные каталоги `BASES`/`BASES_PRD` с `period_sec: 3600`, `cache: true`.
Готовый пример находится в `Backup.example.json`.

Для AutoPad следует указывать локальные пути машины с базами, например
`D:\BASES_PRD`, а не UNC-путь или подключённый сетевой диск. Временные
`-journal`, `-wal` и `-shm` рядом с распознанной SQLite не копируются:
в снимке находится самостоятельный проверенный файл базы.

Если хотя бы одна база внутри каталога не скопировалась или не прошла
`PRAGMA integrity_check`, снимок цели не публикуется, а предыдущие версии
не затрагиваются. Успешно подготовленные файлы остаются в кэше, поэтому
следующий запуск повторяет только изменившиеся или неудачные файлы.

Кэш применяется к AutoPad-базам с rollback-журналом
`DELETE`/`TRUNCATE`/`PERSIST`. Для `WAL` Online Backup выполняется при каждом
запуске; `skip_unchanged` для такой базы также не применяется. В снимок файлы
из кэша копируются физически, поэтому любой каталог
`snapshots\<дата>\data` является полной независимой копией и восстанавливается
без `cache`.

Формат снимков и восстановление описаны в
`docs/BACKUP_SNAPSHOTS.md`.
